## 摘要
我们提出了fabric_ext，一个用于GPU-CXL织物上可扩展操作系统策略的eBPF中间件编译器和运行时。fabric_ext允许一个策略程序在GPU钩子、驱动程序/运行时钩子、DPU/NIC钩子以及CXL交换机或近内存钩子上执行。关键抽象是一个语义移动图：边描述字节、步幅、重用距离、读写比率、源和目标、排序要求、别名集、所有权以及诸如移动、量化、压缩、校验和、过滤、归约、分散/聚集、复制和持久化等转换。编译器将该图降级为每设备eBPF程序、验证器义务、一致性分类的BPF映射以及用于bpftime和dputime的工件。在织物边缘，fabric_ext将近Type-2小核心视为硬件JIT和状态管理器：它将验证过的移动描述符特化为本地复制、放置、排序和转换命令，而周围的冯·诺依曼岛（内存、DMA和计算引擎）执行数据流。由于这种数据流是数据驱动的，fabric_ext还将观察点放置在岛旁边，使得队列、DMA完成、内存放置和所有权转换在发生时可见。典型的压力测试是LLM预填充：注意力流传输KV块和归约，而FFN流传输激活、权重和可压缩中间体，迫使一个请求跨越GPU张量执行、DPU/NIC事件执行以及CXL或交换机本地数据流岛。

## Abstract
We present fabric_ext, an eBPF middleware compiler and runtime for extensible OS policies over GPU--CXL fabrics. fabric_ext lets one policy program execute across GPU hooks, driver/runtime hooks, DPU/NIC hooks, and CXL switch or near-memory hooks. The key abstraction is a semantic movement graph: edges describe bytes, stride, reuse distance, read/write ratio, source and destination, ordering requirement, alias set, ownership, and transformations such as Move, Quantize, Compress, Checksum, Filter, Reduce, Scatter/Gather, Replicate, and Persist. The compiler lowers this graph into per-device eBPF programs, verifier obligations, consistency-classed BPF maps, and artifacts for bpftime and dputime. At the fabric edge, fabric_ext treats a near-Type-2 small core as a hardware-JIT and state manager: it specializes verified movement descriptors into local copy, placement, ordering, and transformation commands, while the surrounding Von Neumann island of memory, DMA, and compute engines performs the dataflow. Because this dataflow is data-driven, fabric_ext also places observation beside the island, where queues, DMA completions, memory placement, and ownership transitions are visible as they happen. The canonical stress case is LLM prefill: attention streams KV blocks and reductions while FFN streams activations, weights, and compressible intermediates, forcing one request to cross GPU tensor execution, DPU/NIC event execution, and CXL or switch-local dataflow islands.

# 《The Fabric Is the Cluster Driver: Cross-Layer eBPF Policies for GPU–CXL Fabrics》论文总结

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：现代 GPU 集群已不再是"宿主机 CPU 后的一堆加速器"，而是由 GPU、DPU/NIC、CXL 交换机/内存设备构成的**异构织物（fabric）**。各层各自掌握部分真相：
  - GPU 层知道执行阶段（prefill/decode）、warp 行为、页错误、KV 块语义、张量含义，但看不到 RDMA 队列深度、拥塞状态或 CXL 内存放置情况。
  - DPU/NIC 层看到队列对（QP）、WQE/CQE、重传、拥塞，但不知道字节属于 decode、prefill、MoE 路由还是 checkpoint。
  - CXL 交换机/内存层看到放置、共享、排序、持久性，但缺乏应用语义（重用距离、别名所有权、阶段信息）。
- **核心问题**：现有控制平面将这些信号割裂在互不感知的策略系统中，导致**语义分裂（semantic split）**——每个本地控制器都在信息不完整的情况下做出决策。例如：GPU 认为 decode KV 获取紧急，但无法直接为拥塞的 RDMA 队列调速；DPU 可以优先调度 QP，但不知道字节的语义类别。
- **核心主张**：可编程的对象应当是**织物本身**，而非单个设备。策略边界应当以织物为界，而非以设备为界。需要一个安全、动态、语义化的策略层，决定数据移动的"是否、何处、何时"（是否移动、变换在哪里执行、何时延迟/重定向/复制/持久化）。

## 2. 提出的方法论：fabric_ext

### 2.1 核心思想

fabric_ext 是一个 **eBPF 中间件编译器与运行时**，允许单一逻辑策略程序跨 GPU 钩子、驱动/运行时钩子、DPU/NIC 钩子以及 CXL 交换机/近内存钩子执行。设计原则是：**数据通路保持设备专用，策略语义全局共享**。

### 2.2 语义移动图（Semantic Movement Graph）

- 编译器的中间表示（IR）是一张语义移动图：
  - **节点**：宿主机内存、CXL 内存设备、GPU 内存、加速器、交换机计算引擎（共 5 类）。
  - **边**（移动意图）携带字段：字节数、步幅、重用距离、读写比、源/目的端、排序要求、别名集、所有权、变换操作。
  - **9 种变换动作**：Move（纯移动）、Move+Quantize、Move+Compress、Move+Checksum、Move+Filter、Move+Reduce、Move+Scatter/Gather、Move+Replicate、Move+Persist。

### 2.3 近 Type-2 硬件 JIT 执行模型

- 在织物边缘，fabric_ext 将 **near-Type-2 小核心**视为**硬件 JIT 与状态管理器**：
  - 将验证过的移动描述符特化为设备本地命令（DMA 拷贝、CXL 放置、持久化、归约、scatter/gather、调速、副本选择）。
  - 管理本地策略状态：映射纪元（epoch）、所有权交接、命令序列号、TTL、能力检查。
  - 数据流由周围的**冯·诺依曼岛**（内存、DMA 引擎、队列机制、小型变换单元）执行。
- **观测旁置（observation sidecar）**：由于数据流是数据驱动的（由队列条目、DMA 完成、内存就绪位触发），观测点也必须放在岛旁，使队列压力、完成时序、所有权转换在发生时即被看见，而非等宿主机轮询。

### 2.4 一致性分类的 BPF 映射（Consistency-Classed BPF Maps）

这是论文的关键设计之一——fabric_ext 拒绝"一刀切"的共享映射，而是按一致性需求将映射分为四类：

| 映射类 | 一致性契约 | 典型状态 |
|--------|-----------|----------|
| Telemetry（遥测） | 最终一致 | 字节数、队列深度、重试计数 |
| Hint（提示） | 有界陈旧（带纪元与过期时间） | decode/prefill/MoE 阶段、专家负载、远端就绪 |
| Ownership（所有权） | 纪元原子交接 | CXL 内存窗口、GPU 缓冲区所有权、QP 能力绑定 |
| Command（命令） | 恰好一次完成（带序列号） | 重定向、重试、持久化、归约、放置提交 |

### 2.5 跨设备效应验证器（Cross-Device Effect Verifier）

验证器在传统 eBPF 有界执行检查基础上，增加了织物效应检查：
1. 各处理器有界指令数、helper 数、栈使用量。
2. 处理器不能等待由同一处理器尚未发出的操作才能产生的完成事件。
3. GPU 与织物处理器之间不能形成依赖环。
4. 所有 QP、租户、GPU 内存区域、CXL 窗口访问受能力（capability）保护。
5. 每个输入事件产生有界数量的 RDMA/DMA/CXL 操作。
6. 重定向与重试路径携带 TTL，防止活锁。
7. GPU 与织物程序通过纪元原子切换更新（epoch-atomic switch）。

### 2.6 放置与降级策略

编译器根据源/目的端、变换类型、字节量、重用距离、排序要求和设备能力决定变换执行位置：
- **GPU 预变换**：源数据在 HBM 且变换缩小数据（量化、压缩、过滤、归约）时优先。
- **DPU/NIC 内联**：RDMA 队列调度、副本选择、调速、校验和等已在网络路径上的操作。
- **CXL 交换机/近内存执行**：源或目的端为 CXL 内存时，放置、持久化、拷贝、归约、scatter/gather 优先。
- **宿主机执行**：作为不支持设备时的回退、策略加载与审计。

## 6. 主要结论与发现

1. **编译器可覆盖移动原语空间并产出真实 BPF 工件**：1,000 个微基准全部通过验证，编译时间中位数 8.5μs，BPF C 生成时间中位数 4.1μs，支持运行时策略迭代。
2. **跨设备打包路径有效**：14 个工作负载生成的 86 个 BPF 对象全部在 BlueField DPU OS 上远程重编译成功。
3. **语义策略带来显著的建模 E2E 改进**：
   - 一级 fabric_ext：聚合加速比 **2.34×**（相对分阶段宿主机/NIC 控制）。
   - 复制路径优化后：聚合加速比提升至 **3.47×**。
4. **不同事件的最佳执行点不同**：
   - DPU 内联：适合大拷贝与持久化路径（如 KV 副本刷新、checkpoint 持久化）。
   - GPU 预变换：适合 HBM 侧缩小数据量的变换（如压缩、归约、量化）。
   - CXL 交换机/近内存执行：适合放置、所有权、持久性、内存本地归约。
5. **加速比随 GPU 数量增加而下降**（2.76×→1.96×），因为副本刷新与 checkpoint 持久化变为字节量主导，语义策略无法隐藏全部织物工作——扩展越大，语义策略的相对收益越小。
6. **路径组合的额外收益**：最优点路径混合为 49 个 DPU 内联、24 个 GPU 预变换、13 个直连 GPU peer/CXL；对关键优先级事件额外加速 1.51×。

## 7. 优点

- **问题选取精准**：准确识别了 GPU 织物中"语义分裂"这一真实且重要的控制平面问题。
- **设计创新性强**：
  - 语义移动图作为跨设备策略的中间表示，兼具表达力与可验证性。
  - 一致性分类映射解决了"不同状态需要不同一致性保证"这一核心正确性问题（遥测可最终一致，所有权必须纪元原子）。
  - 近 Type-2 硬件 JIT 模型将策略控制与数据流分离，避免了"小核心逐字节拷贝"的低效陷阱。
  - 跨设备效应验证器将 eBPF 验证从单设备扩展到跨设备依赖环、TTL、能力检查，是实质性贡献。
- **工作负载选择合理**：LLM prefill、MoE、远程 KV 缓存等场景确实需要跨层语义协调，论证充分有力。
- **实现与评估兼顾工程可行性**：生成了真实 BPF 对象并在 DPU 上远程编译验证，而非纯纸上架构。
- **主观诚实**：明确区分建模加速比与真实 token 延迟，不夸大为端到端性能声明。

## 8. 不足与局限

- **缺乏真实硬件部署验证**：CXL 交换机/近 Type-2 后端仅通过接口建模，未在真实可编程 CXL 交换机或 Type-2 设备上部署；作者也承认这是主要限制。
- **E2E 加速比为纯建模结果**：基于显式数据移动模型，未包含真实网络协议开销、设备固件延迟、运行时集成成本，加速比数值（2.34×/3.47×）需谨慎解读。
- **对比基线较弱**：仅为"分阶段宿主机/NIC 控制"，未与现有成熟替代方案（NCCL 调优、纯 DPU offload、CXL fabric manager 策略、GPU 本地 eBPF 系统）直接对比。
- **缺失消融实验**：未单独评估各组件（一致性映射类、验证器、放置算法、近 Type-2 模型）的独立贡献。
- **算力信息缺失**：未报告 GPU 型号、数量、集群拓扑等关键资源信息，无法评估结果的可复现性和硬件相关性。
- **未验证语义正确性**：验证器只保证有界执行与效应安全，不保证用户策略的语义正确——"一个有界但糟糕的策略仍会选择错误的优先级"（作者自认）。
- **真实部署障碍未充分讨论**：每个硬件目标仍需专用后端将验证决策映射到设备特定机制；厂商特定附加点（attach points）是落地的主要工程障碍。
