## 摘要
处理内存（PIM）系统由许多具有小型本地内存的处理器组成，近年来已作为商业产品出现，并作为克服内存墙的一种手段而备受关注，特别是在内存数据库技术背景下。最先进的面向PIM的索引PIM-tree已被证明能够实现渐近良好的时空负载均衡——在偏斜查询下，查询负载和数据大小在处理器之间达到平衡——通过牺牲空间局部性。然而，这种空间局部性的牺牲阻碍了面向PIM的范围聚合查询处理。为了在PIM系统上同时实现时空负载均衡和高效执行范围聚合查询，我们开发了一种基于查询密度的键范围分区方案。它在PIM处理器之间平衡查询密度，并允许我们通过一个参数在查询负载和数据大小之间取得平衡。然后，我们基于该分区方案开发了B$^+$-Forest，一种面向PIM的B$^+$-树变体。实验结果表明，与基于空间约束、查询负载均衡、密度无关分区的B$^+$-树相比，它具有更高的抗偏斜性，在点查询中性能与PIM-tree相当，并高效支持范围聚合查询。

## Abstract
Processing-in-Memory (PIM) systems, which consist of many processors with small local memory, have recently emerged as commercial products and attracted much attention as a means of overcoming the memory wall, particularly in the context of in-memory database technology. The state-of-the-art PIM-oriented index PIM-tree has been demonstrated to achieve asymptotically good spatiotemporal load balancing---query loads and data sizes are balanced among processors---for skewed queries, by trading spatial locality. Unfortunately, such a sacrifice of spatial locality hinders the PIM-oriented processing of range-aggregate queries. To achieve both spatiotemporal load balancing and efficiently executing range-aggregate queries on PIM systems, we develop a query density-driven key-range partitioning scheme. It balances query density among PIM processors, allowing us to strike a balance between query load and data size via a parameter. We then develop B${}^\text{+}$-Forest, a PIM-oriented B${}^\text{+}$-tree variant based on our partitioning scheme. Experimental results demonstrated that it exhibits higher skew resistance than a B${}^\text{+}$-tree based on space-constrained, query-load-balanced, density-unaware partitioning, and performance comparable to PIM-tree in point-get queries, as well as efficient support for range-aggregate queries.

### 1. 论文的核心问题与整体含义（研究动机和背景）

- **背景**：随着数据密集型计算的发展，“内存墙”问题日益严峻——物理数据移动带来了不可避免的开销。Processing-in-Memory（PIM）系统通过将数据分布到大量配备小型本地内存的处理器上，并行处理数据以减少数据移动，成为突破内存墙的重要途径。UPMEM PIM 是首个商用的真实 PIM 系统，其计算模型由 CPU 主机和大量称为 DPU 的 PIM 处理器构成（每个 DPU 仅有 64 MiB DRAM 和 400 MHz 的处理器）。
- **核心挑战**：在 UPMEM PIM 这类“多处理器 + 小本地内存”的系统上构建内存键值存储索引时，必须实现**时空负载均衡**（spatiotemporal load balancing）——即在偏斜查询（skewed queries）下，既要平衡各 DPU 上的查询负载（时间维度），又要平衡分配给各 DPU 的数据大小（空间维度），以满足硬件资源约束。
- **现有方案的矛盾**：最先进的 PIM 索引 PIM-tree 通过将键空间随机打散为细粒度块来实现渐近良好的时空负载均衡，但其代价是**牺牲空间局部性**——长范围查询会跨越大量 DPU，导致 CPU 与 PIM 之间的通信大幅放大。空间局部性的丧失对高效执行**范围聚合查询（RAQs）** 尤为不利，因为用户自定义聚合函数无法很好地利用 PIM-tree 的查询融合机制。因此，**“同时实现偏斜查询下的时空负载均衡与高效的范围聚合查询处理”** 是该领域的一个开放挑战。
- **本文目标**：提出一种基于**查询密度**（query density，即单位数据量上的命中查询数）驱动的键范围分区方案，在保持空间局部性的前提下实现时空负载均衡，并在此基础上开发 B⁺-Forest 索引，以高效支持范围聚合查询。

### 2. 论文提出的方法论

#### 2.1 核心思想

- **关键观察**：查询密度（单位数据大小上的命中查询数）的显著差距会转化为 DPU 间查询负载或数据大小的不平衡。现有方案（如 PIM-tree）通过将数据细粒度随机打散来混合热/冷区间，实现查询密度均衡，但这样做破坏了空间局部性。
- **核心思路**：采用**粗粒度分区 + 热点精准识别与分发**的策略——识别出查询密度高的“热区间”（hot ranges），将其切分出来并分发到各个 DPU（使每个 DPU 至少至多一个热分区），而剩余的“冷区间”（cold ranges）则以块连续的方式均匀分布在 DPU 上。这样既保证了偏斜查询下各 DPU 的查询负载均衡，又保留了大部分数据的空间连续性，有利于范围聚合查询。

#### 2.2 分区方案总览（Algorithm 1）

分区算法整体流程如下：

1. **形成基础分区**：将按键排序的数据均匀划分为 $P$ 个基础分区（与 DPU 数量相同），使数据大小均衡。
2. **识别热区间**：在每个基础分区内调用 FindHot 过程，提取出查询密度高的热区间。
3. **形成冷分区**：移除热区间后剩余的即为冷区间。
4. **分发热分区**：按照冷分区上查询负载从低到高的顺序，将热分区依次分配给各 DPU，且每个 DPU 至多接收一个热分区。

该设计将总分区数限制在至多 $3P$ 个，路由表可放入 CPU 缓存，减少查询路由开销。

#### 2.3 贪婪热区间选择算法（Algorithm 2）

基于参数 $\alpha$（基础分区数据大小与热分区最大宽度之比，$\alpha$ 越大越偏重数据均衡，越接近 1 越偏重查询负载均衡）：

- 以数据大小为 $ \frac{1}{\alpha} \cdot \frac{D}{P}$ 的窗口扫描基础分区；若窗口内查询数超过阈值 $Q/P$（$Q$ 为参考工作负载总查询数），则将该窗口选为热分区。
- 该算法保证：每个热分区的数据量 < $\frac{1}{\alpha}\frac{D}{P} + M_d$，查询量 < $\frac{Q}{P} + M_q$；冷分区在单个 DPU 上的查询负载 < $\alpha\frac{Q}{P}$；总热区间数不超过 $P$。

#### 2.4 双扫描热区间选择算法（Algorithm 3）

贪婪算法在 $\alpha$ 较大时可能找不到足够的热区间，导致部分 DPU 近乎空闲。双扫描扩展在此基础上进行第二次扫描：

- 根据第一次扫描后剩余查询数计算 $\beta$（需要补充选取的热区间数量，约为剩余查询量除以 $Q/P$）。
- 以更宽窗口（$ \frac{\beta}{\alpha}\cdot\frac{D}{P}$）寻找剩余查询量最大的位置，将其按数据量均分为 $\beta$ 份选为新的热区间。
- 该算法将冷分区上的查询负载上限从 $\alpha \cdot Q/P$ 降低到 $\frac{\alpha+1}{3} \cdot Q/P$（当 $\alpha=10$ 时约减少 63%），且保持数据大小上限不变。

#### 2.5 计算成本

分区算法的时间复杂度为 $O(P + N)$（$N$ 为数据块数）。论文指出，即使最坏情况下的全量重分区，成本也比键值对的（反）序列化和数据传输低约三个数量级。

#### 2.6 B⁺-Forest 索引

- **数据表示**：每个 DPU 维护两个 B⁺-树（分别存储冷分区和热分区的数据）；路由表由分区边界数组和目标 DPU 数组组成（共两个数组），通过二分搜索加线性搜索确定 RAQ 的目标 DPU。
- **查询处理**分为三步：
  1. **路由（Routing）**：CPU 根据路由表将一批 RAQ 分解为每个 DPU 的子批次，并记录 RAQ ID 供后处理使用。
  2. **求值（Evaluation）**：DPU 在本地 B⁺-树上执行子批次中的 RAQ，计算部分聚合结果，无需同步。
  3. **后处理（Postprocessing）**：CPU 收集部分结果，按输入顺序聚合，输出最终结果（无锁、无同步设计）。

### 6. 论文的主要结论与发现

1. **查询密度驱动分区显著优于密度无感知分区**：在较严重的数据偏斜下（Zipf 约 1.0），密度无感知分区的查询不平衡因子随偏斜加剧而上升，而查询密度驱动分区（双扫描版）能保持近乎恒定的不平衡因子；在大多数情况下批处理时间也随负载均衡改善而下降。
2. **双扫描扩展有效**：相比基本贪婪算法，双扫描算法能选出更充分的热分区，减少空闲 DPU，在 Zipf 约 1.0 时显著降低查询不平衡因子。
3. **参数 $\alpha$ 为实用调优提供了权衡空间**：无论偏斜程度如何，增大 $\alpha$（放宽数据均衡）都能有效降低批处理时间；因此可根据可用内存容量选择“最佳点”。
4. **扩展性在 DPU 较多时受限**：性能在 $P=1012$ 前随 DPU 数量扩展，但在 $P=2538$ 时部分场景性能恶化，主要原因是数据分块带来的负载均衡误差增大以及 CPU 端路由/后处理开销增加（数据越小、偏斜越严重时越明显）。
5. **工作负载漂移的脆弱性**：当参考工作负载偏移时，冷分区中原本密度较高的部分最可能成为性能瓶颈；在特定场景下（ZcAmp($b_{20}$, 10)），不平衡因子从 2.8 飙升至 26。
6. **B⁺-Forest 性能与 PIM-tree 可比且功能更丰富**：在点查询（get）上，B⁺-Forest 在 Zipf ≤ 1.0 时优于 PIM-tree，在 Zipf = 1.2 时略逊（PIM-tree 的查询融合在更偏斜时优势更大）。但 B⁺-Forest 能高效支持 RAQ（RAQ 吞吐量达到 get 查询的 44.2% 以上），且能处理远大于 PIM-tree 的查询批次（1.1G 对比 1M/5M），大批次下吞吐量更高、偏斜敏感度更低。
7. **对偏斜的抵抗力来自查询密度驱动的分区而非简单的一维分区**：数据均衡分区在 Zipf=1.0 时查询不平衡因子高达 334，而查询均衡分区导致数据不平衡因子达 10.2，均不满足要求。

- **问题洞察深刻**：明确提出“查询密度”这一关键指标，并通过“识别热区间 + 单独分发”而非随机打散的方式实现偏斜下的时空负载均衡，在设计中同时兼顾了空间局部性，切中 PIM 系统上 RAQ 处理的痛点。
- **方案设计优雅、可扩展**：
  - 分区数量控制在 $O(P)$ 级别（至多 $3P$），路由表可完全容纳于 CPU 缓存；
  - 分区算法的时间复杂度仅 $O(P + N)$，并且热区间选择可在各 DPU 上并行执行，具有 PIM 友好的特性；
  - 提供参数 $\alpha$ 让使用者根据硬件内存约束灵活调节负载均衡与数据均衡的优先级。
- **理论基础扎实**：提供了双扫描算法的完整正确性与界限证明（附录 A、B），包括数据/查询负载上界的严格推导。
- **实验对比公平**：在与 PIM-tree 比较时特意使用 PIM-tree 最优参数（更多 DPU、更少线程数、合适的批大小），避免了对己方方案的无意偏袒；同时对冷/热区间分配不均、工作负载漂移等弱点也进行了曝光分析，态度客观。
- **工程实践落地**：实现了完整的 B⁺-Forest 原型，支持无锁、无同步的三阶段批处理流程。

### 8. 不足与局限

- **离线重分区的局限**：论文仅讨论基于参考工作负载的离线全量重分区，未解决动态工作负载变化下的在线重分区问题（作者声明在并行论文中处理该问题）。这限制了在真实环境下应对工作负载漂移的能力（实验 6.4 也证实了这一脆弱性）。
- **实验数据的局限**：全部实验使用合成数据（均匀分布的键 + Zipf 复合分布查询），未使用真实世界数据集（如 RocksDB 的 Facebook 工作负载跟踪数据），可能无法完全代表真实工作负载的特征。
- **与最先进方法的比较不够全面**：未与另一种热感知 PIM 索引 RADAR 进行直接对比；在范围查询方面，与 PIM-tree 不是直接可比（B⁺-Forest 支持 RAQ，PIM-tree 支持范围扫描+查询融合），论文只能提供间接的对比证据。
- **PIM-tree 对比的实验条件受限**：B⁺-Forest 和 PIM-tree 使用不同的 DPU 数量、线程数和批大小（虽是为公平考虑），但这也意味着比较不够“苹果对苹果”；且 PIM-tree 公开代码的“最小修改”可能引入微小性能差异。
- **数据分块的副作用**：负载均衡建立在数据块粒度上，当一个块接收到大量查询时会造成不可避免的负载不均衡；在块粒度较粗或查询偏斜更严重时，这一副作用愈加明显，成为扩展性受限的重要原因。
- **硬件依赖与适用性限制**：B⁺-Forest 不适用于锁步型 PIM 架构（如 HBM-PIM）；UPMEM PIM 已于 2025 年停产，但作者指出该模型可类比适用于 MPPA 架构（如 Kalray、PEZY），这一推广尚属展望，缺乏实验验证。
