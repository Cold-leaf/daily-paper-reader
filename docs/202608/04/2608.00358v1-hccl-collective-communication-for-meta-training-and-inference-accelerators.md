## 摘要
我们提出了HCCL，这是一个与Meta的MTIA 300加速器协同设计的集合通信库，MTIA 300是Meta首款将后端网络直接集成到芯片封装上的芯片。MTIA 300包括专用的消息引擎（ME），具有近内存计算（NMC）功能，可将集合执行完全从计算网格中卸载，从而实现计算与通信之间的大规模重叠。HCCL采用编译通信模型，其中主机生成每个集合（包括依赖关系）的完整描述。我们描述了控制和数据路径架构、跨MTIA 300非对称扩展和扩展网络拓扑感知算法选择，以及针对训练和推理工作负载的优化。对于训练，HCCL在机架内集合上实现高达940 GB/s的吞吐量，同时对并发计算吞吐量的影响小于0.5%。对于推理，我们利用绕过调度路径的单边通信原语来最小化集合延迟，并描述了改进计算-通信流水线处理以适用于延迟敏感工作负载的集合设计。

## Abstract
We present HCCL, a collective communication library co-designed with Meta's MTIA 300 accelerator, the first Meta chip to integrate backend networking directly on chip package. MTIA 300 includes dedicated message engines (MEs) with near-memory compute (NMC) that fully offload collective execution from the compute grid, enabling large overlap between computation and communication. HCCL uses a compiled communication model in which the host generates a complete description of each collective including dependencies. We describe the control and data path architecture, topology-aware algorithm selection across MTIA 300's asymmetric scale-up and scale-out network, and optimizations for both training and inference workloads. For training, HCCL achieves up to 940 GB/s on intra-rack collectives while introducing less than 0.5% degradation to concurrent compute throughput. For inference, we leverage one-sided communication primitives that bypass the scheduling path to minimize collective latency and describe collective designs that improve compute-communication pipelining for latency-sensitive workloads.

## 1. 论文的核心问题与整体含义（研究动机和背景）
- **背景**：Meta 的排行与推荐模型服务数十亿用户，具有大规模 embedding 表、以 AllToAllv 为主的非规则通信模式，并且需要在上百个加速器上扩展训练。随着模型复杂度增长，通信在总训练时间中的占比越来越高，集合通信库的效率成为端到端性能的关键。
- **动机**：Meta 开发了自定义加速器 MTIA 芯片系列，MTIA 300 是第三代，也是首款将后端网络直接集成到芯片封装中的 Meta 芯片。传统 GPU 架构（如 GPU+网卡）的通信路径涉及主机-设备-NIC 多次拷贝，而 MTIA 300 通过片上集成网络为“将整个集合操作卸载到专用硬件”提供了新可能。
- **核心问题**：如何为 MTIA 300 设计并实现一个与硬件协同优化的集合通信库，在训练场景中最大化带宽利用率，同时在推理等延迟敏感场景中最小化通信延迟，且不消耗计算网格资源。
- **整体含义**：论文提出 HCCL（Hoot Collective Communication Library），通过专用消息引擎（ME）、近内存计算（NMC）和编译通信模型，将集合通信完全从计算网格卸载，实现计算与通信的大规模重叠；同时通过单向通信和设备触达型集合设计，兼顾推理所需的低延迟。

## 2. 方法论：核心思想、关键技术细节、算法流程
### 核心思想
- **硬件与软件协同设计**：HCCL 与 MTIA 300 的硬件通信能力（消息引擎、NMC、自定义 RDMA NIC）深度耦合，不是把集合通信当作计算 kernel 在计算网格上执行（如 NCCL/RCCL），而是由主机生成完整的“子图”描述，交给专用 ME 自主执行。
- **编译通信模型**：主机（CPU-C）为每个集合生成包含所有依赖关系的完整描述（工作包 → 子图 → WQE），一次性提交给 ME 执行，不再需要计算网格参与。

### 关键技术细节
1. **MTIA 300 通信硬件**：
   - **控制核 CPU-C**：负责流内顺序和跨流依赖，将子图调度到对应 ME。
   - **消息引擎 ME**：芯片含 2 组共 16 个 ME，每个 ME 有 CPU-M（RISC-V 通信核）、NIC 接口、NMC 三部分。
   - **NMC（近内存计算）**：支持数据拷贝与和归约（如 S=A+B、A=A+B 等），总带宽 2.8 TB/s，支持 BF16、FP16、FP32，原生 FP32 运算并重量化。
   - **网络 chiplet**：每个 chiplet 含 6 个 800Gb/s RDMA NIC，共 12 个 NIC；采用 **Express Doorbells** 机制，将 WQE 写入本身作为 doorbell，省去从外部队列读取 WQE 的开销；NIC 内存有限，因此不支持 QP 缓存。
   - **非对称 scale-up / scale-out**：初始配置 2 个 NIC 用于 scale-out、8 个用于 scale-up，总带宽 1 TB/s，另有 2 个 NIC 可增至 1.2 TB/s。

2. **HCCL 控制路径**：
   - 使用标准 RDMA verbs 管理 QP、MR 等资源，按需动态分配 QP，复用空闲 QP 以适配 Express Doorbell 的队对数量限制。
   - 控制路径集中在减少算法所需的最少 QP 数量，而不是靠大量 QP 扩展性能。

3. **HCCL 数据路径**：
   - 以“流”为单位，流内按工作包顺序执行（类似 compute kernel），每个工作包可拆分为多个子图并行到多个 ME 上。
   - 子图由 WQE 组成，支持三类 WQE：RDMA 传输（Send/Receive/Write）、计算操作（NMC 求和/拷贝）、子图协调（wait/update memory）。
   - **五种依赖类型**：Fence（当前 WQE 完成才继续）、Sync（所有之前 WQE 完成）、WQE Sync（等待特定 WQE）、Receive Sync（所有接收 WQE 完成）、Send Sync（所有发送 WQE 完成）。
   - 算法示例：AllReduce 环形算法可通过多个 send/receive/add WQE 及依赖构建（如图 5）。
   - 采用 **SendSync 协议**（responder 驱动的信号机制）避免 RNR（Receiver Not Ready）重试，只在集合第一个传输使用完整协议，后续由算法保证接收端已预备。

### 优化方法
- **训练优化**：并行 ME 处理，把 AllReduce 拆成多环、AllToAllv 切片分散到多子图，提高注入率和吞吐。
- **推理优化**：
  - **单向通信（One-sided）**：PE 通过 Express Doorbell 直接提交 WQE，ME 只负责完成通知和计数器，PE 轮询计数器，绕开调度路径。
  - **设备驻留集合（Device-resident）**：AllToAllvDynamic 接收设备内存中的元数据指针，由设备直接修改 WQE，避免主机软件栈重新生成子图。
  - **设备触达集合（Device-triggered）**：集合可在独立流中预启动，通过内存地址+比较器等待计算 kernel 发出信号后才真正执行，完成后触发下一个计算，减少图模式中的 graph break 和调度延迟。

## 6. 论文的主要结论与发现
- **训练性能**：HCCL 在机架内（scale-up 域）集合通信中达到最高 **940 GB/s** 的实测带宽，接近理论峰值；跨机架场景下能通过拓扑感知算法平衡 scale-up/scale-out 用量，例如 128 ranks AllGather 仍可达 838 GB/s。
- **计算-通信重叠**：在 GEMM 饱和计算网格的同时执行集合通信，计算吞吐退化仅约 **0.5%**（低于 1 TFlop），证明专用 ME 卸载方案能有效解放计算核心。
- **控制核与调度开销**：CPU-C 分派约 2.9μs，CPU-M 执行约 1.1μs，事件处理 3.6μs，H2D 拷贝 17.1μs（但实际可被流水线隐藏）；缓存后的工作包重排队开销小于 10μs。
- **推理延迟**：从 PE 直接提交单向 RDMA WQE 比从 ME 提交节省约 **450 ns** 静态开销；设备触达集合可把集体通信的实际计算流暴露时间从 123μs 降到 31μs；PE 网格上的 put 风格 AllReduce/AllToAllv 可实现 **sub-6μs** 集合延迟。
- **总体结论**：硬件卸载 + 编译式通信模型可以同时满足训练（带宽密集）和推理（延迟敏感）的需求，为未来 MTIA 芯片奠定了通信原语和架构基础。

## 7. 优点：方法或实验设计上的亮点
- **真正的全硬件卸载**：HCCL 不像 NCCL 在 GPU SM 上跑 kernel，而是用专用 ME + NMC 执行集合，实现计算网格的零占用。
- **编译通信模型**：主机一次性生成含依赖关系的子图，ME 自主执行，控制路径和数据路径分离，支持工作包级缓存，降低调度开销。
- **硬件-软件协同设计**：Express Doorbell、NMC 归约、内存分区标记等硬件特性与软件语义（WQE 类型、依赖类型）深度匹配。
- **面向真实负载**：先从推荐/排序训练负载的通信分布出发确定优化目标（AllToAllv、AllReduce、AllGather），针对性和实用性强。
- **推理专项优化**：引入单向通信、AllToAllvDynamic、设备触达集合和 PE kernel 集合，在图模式中实现计算-通信流水线，减少 graph break 和调度延迟。

## 9. 对领域的主要贡献与启示
- **提出了一种可复用的硬件-软件协同通信库范式**：HCCL 证明了“编译通信模型 + 专用硬件卸载”能够同时兼顾高带宽和低延迟，为其他定制加速器（如 TPU、LPU 等）的通信栈设计提供了参考。
- **丰富了集合通信的实现维度**：传统集合通信库以 kernel 或纯软件算法为主，HCCL 展示了一条“WQE 驱动 + NMC 计算 + 非对称网络”的路径，扩展了该领域的设计空间。
- **为推理场景的集合通信提供了新思路**：通过设备触达集合和 PE 直接提交 WQE，显著降低了图模式中的调度开销，这对大模型推理、PP/EP 并行场景具有重要意义。
- **开源与技术传播的遗憾**：论文未提及 HCCL 是否开源，相关实现细节受限于 Meta 内部硬件，可能使得该成果对学术社区的可复现性较低。

## 10. 个人思考与展望
- 从算法到硬件的协同设计是系统性能提升的关键，HCCL 的收益本质上来自将“语义明确的操作”（如归约、传输）下沉到专用硬件，同时用编译子图最小化控制开销。未来若能在通用 GPU 上实现类似硬件抽象（如 DPU 或 SmartNIC 上的集合原语），也能部分受益。
- 小消息延迟仍是短板，这与硬件固定开销有关；未来可通过减少门铃开销、优化接收端轮询机制或使用带宽专用通道来进一步压缩。
- 论文对训练端到端性能的验证仍有限，缺少与真实训练任务（如 DLRM、LLM）的联合端到端对比；建议后续工作补充实际训练吞吐和收敛速度的评估。
- 通信库的易用性和可编程性同样重要：HCCL 的“编译子图”机制强大，但若需要支持用户自定义集合算法，可能需提供更灵活的编程接口，避免每次修改都要重新编译整个子图。
- 总体而言，HCCL 是面向下一代 AI 基础设施的勇敢尝试，它对通信路径的重构和硬件卸载的深度执行，可视为集合通信领域的重要里程碑之一。
