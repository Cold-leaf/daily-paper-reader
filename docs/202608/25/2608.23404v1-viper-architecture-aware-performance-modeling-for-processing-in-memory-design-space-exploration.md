## 摘要
处理内存（PIM）有望通过在内存中或内存附近执行计算来减少数据移动开销，但其实际应用加速仍然高度依赖设计。不可卸载的主机执行、主机与PIM之间的传输、有限的PIM容量以及设备编程延迟都可能限制端到端的加速效果，这使得快速的早期设计空间探索（DSE）至关重要。然而，现有的PIM评估方法仍然存在局限：电路级和设备级工具无法捕捉这些端到端的PIM性能因素，而周期精确仿真对于迭代式DSE来说速度太慢。为了解决这一差距，我们提出了VIPER，一个用于PIM DSE的统一、轻量级且架构感知的性能评估框架。VIPER对主机执行进行一次剖析，并将测得的主机行为与一个感知PIM的分析引擎相结合，该引擎在候选设计间扫描PIM侧参数。它通过捕捉主机-PIM传输、阵列访问、内存内计算、设备编程延迟以及容量引起的分区，支持任务卸载和数据触发执行下的近内存处理（PNM）和内存内处理（PUM），为迭代式DSE提供快速的架构感知性能估计，而无需重复进行周期精确仿真。我们针对商业化的UPMEM系统和超过400个周期精确的gem5配置对VIPER进行了验证。VIPER能先验地预测UPMEM的卸载决策和盈亏平衡区域，并通过精细化的传输模型，在DPU扫描中捕捉到测得的峰值与滚降行为，平均加速比误差为12%（在256-DPU峰值之前为6%）。与gem5相比，VIPER的误差小于10%，同时将评估时间从数小时缩短到不到一分钟。对UPMEM、ReRAM/FeFET交叉阵列和IMCRYPTO的案例研究表明，架构感知的DSE揭示了设备级评估所遗漏的关键性能权衡。

## Abstract
Processing-in-Memory (PIM) promises to reduce data movement overhead by executing computation in or near memory, but its realized application speedup remains highly design-dependent. Non-offloadable host execution, host-PIM transfers, limited PIM capacity, and device programming latency can limit end-to-end speedup, making fast early-stage design-space exploration (DSE) essential. However, existing PIM evaluation methods remain limited: circuit- and device-level tools cannot capture these end-to-end PIM performance factors, while cycle-accurate simulation is too slow for iterative DSE. To address this gap, we present VIPER, a unified, lightweight, and architecture-aware performance evaluation framework for PIM DSE. VIPER profiles host execution once and combines the measured host behavior with a PIM-aware analytical engine that sweeps PIM-side parameters across candidate designs. It supports both Processing Near Memory (PNM) and Processing Using Memory (PUM) under task-offloading and data-triggered execution by capturing host-PIM transfer, array access, in-memory computation, device programming latency, and capacity-induced partitioning, providing rapid architecture-aware performance estimates for iterative DSE without repeated cycle-accurate simulation. We validate VIPER against a commercial UPMEM system and more than 400 cycle-accurate gem5 configurations. VIPER predicts the UPMEM offloading decision and break-even region a priori, and, with a refined transfer model, captures the measured peak-and-rolloff behavior with 12\% mean speedup error across the DPU sweep (6\% up to the 256-DPU peak). Against gem5, VIPER achieves less than 10\% error while reducing evaluation time from hours to under one minute. Case studies of UPMEM, ReRAM/FeFET crossbars, and IMCRYPTO show that architecture-aware DSE reveals key performance trade-offs that device-level evaluation misses.

## 1. 核心问题与整体含义

- **研究背景**：处理内存（Processing-in-Memory, PIM）通过在内存中或内存附近执行计算来缓解数据移动瓶颈，但其实际端到端加速效果高度依赖于体系结构设计选择，例如不可卸载的主机执行、主机–PIM 数据传输、PIM 容量限制以及 NVM 设备编程延迟等。
- **现存问题**：
  - 电路/器件级工具（如 IMAC-Sim、Eva-CAM）只关注阵列边界，无法捕捉 CPU 交互、数据移动、容量不足等端到端因素；
  - 周期精确全系统模拟器（如 gem5-X、PIMSim）完整但单配置需 6–30 小时，难以支撑迭代式设计空间探索（DSE）；
  - 既有分析模型（如 LogCA、Gables）虽快，但将主机和内存简化成接口成本，无法表达 PIM 特有的容量分区、设备编程延迟和数据触发执行。
- **目标**：提出 VIPER，一种轻量级、架构感知的分析性性能评估框架，能够在秒级时间内支持 PNM 和 PUM 两种范式、任务卸载和数据触发两种执行模型的设计空间探索，并保持与周期精确模拟相当的准确性。

## 2. 方法论

- **核心思想**：将 PIM 视为内存层级中的一个组件，而非主机外挂加速器；基于经典 AMAT（平均内存访问时间）模型扩展 PIM 特有的时序和容量项，使设备物理、架构和数据移动成本都进入内存访问路径。
- **一次性主机剖析**：使用 Linux perf 采集指令数、周期数、L1/LLC 访问和缺失等硬件计数器，导出固定的 CPU 侧参数（执行 CPI、内存访问率、AMAT、时钟周期）。
- **PIM 侧参数扫描**：设计者根据任务卸载或数据触发流程，扫描 PIM 侧参数（指令数、PIM 执行 CPI、PIM 时钟、设备容量、PIM 内存延迟）。
- **任务卸载模型**：
  - 总执行时间 = CPU 执行项 + PIM 执行项；
  - PIM 项中的内存延迟 `t_PIM,mem` 为：
    - PNM：`(tin + tarray + tout) / CC_PIM`（主机到 PIM 传输、阵列到处理单元的数据移动、输出传输）；
    - PUM：`(tin + tprog + tout) / CC_PIM`（用 NVM 单元编程延迟 `tprog` 替代 `tarray`）；
  - 当工作集超过 PIM 容量时，采用分区系数 `m_PIM = ceil(D_PIM / C_PIM)` 作为乘数。
- **数据触发模型**：
  - 将标准 AMAT 中的 `t_DRAM` 替换为 `t_PIM,mem`；
  - 总执行时间只包含 CPU 项，但每次主存访问都经过 PIM；
  - `t_PIM,mem` 包含 `tin + tarray/tprog + tcomp + tout`，并对容量分区乘以 `ceil(D_PIM/C_PIM)`。
- **（算法流程）**：先用 perf 剖析主机应用得到 CPU 基线 → 设计者选择执行模型并扫描 PIM 参数 → VIPER 依据公式 2/4 计算出端到端执行时间、加速比、盈亏平衡点和 Amdahl 上限。
- **模型假设**：AMAT 假设顺序停顿，不建模内存级并行（MLP）；论文认为这适用于早期设计阶段，可作为保守基线，且即便在乱序执行下仍能保持趋势预测能力。

## 3. 实验设计

  - 扫描参数：tile 大小（6 种）、FPU 计算延迟 c（7 种，其中 4 种符合真实流水线 MAC 深度，3 种为压力值）、scratchpad 延迟 m（8 种，m=0 模拟 PUM，m>0 模拟 PNM），共 336 个配置；
  - 指标：VIPER 预测与 gem5 端到端延迟的误差和趋势吻合度。
- **数据触发验证（扩展 gem5-SALAM）**：
  - 在缓存/内存控制器中注入 PIM 延迟，模拟 11 种配置（覆盖 SRAM/DRAM/HBM/NVM/storage，触发器位于 L1 后、LLC 后、DRAM 内，含顺序和乱序 CPU）；
  - 基准：SPEC2017（多个 benchmark）+ GraphBig（GitHub 数据集），共 12 个 benchmark，132 个 benchmark–配置组合；
  - 对比归一化延迟（PIM 延迟/无 PIM 基线延迟）。
- **真实硬件验证（UPMEM）**：
  - 2,560-DPU UPMEM 服务器（350 MHz，SDK 2025.1.0，Intel Xeon Silver 4215 主机）；
  - 单层 Llama2 matmul offload，对比 VIPER 先验预测与实际测量。
- **案例研究**：

## 6. 主要结论与发现

- **准确性**：在 400+ gem5 配置上，VIPER 平均误差低于 10%，97% 的任务卸载预测点落在 ±10% 包络内；数据触发实验在顺序 CPU 上相关系数 r=0.995，乱序 CPU 上 r=0.994。
- **UPMEM 验证**：VIPER 能先验预测卸载决策、盈亏平衡 DPU 数（预测 35，实测约 40–49）和 Amdahl 上限（6.57×）；但最初固定的传输模型无法预测实测“峰值–滚降”行为，将传输时间改为随 DPU 数线性增长后，VIPER 成功复现了约 256 DPU 附近的峰值加速比。
- **关键设计洞见**：
  - 端到端加速主要受主机不可卸载工作和 CPU–PIM 传输限制，而非 PIM 设备本身的计算速度；
  - 交叉阵列容量略小于工作集时，性能反而远差于更小的阵列（因反复分区和重载）；
  - 同一 PIM 设计在不同存储技术下可行性不同（IMCRYPTO 用 CMOS/FeFET 可满足 10% 开销预算，而 RRAM/PCM 不行）。
- **总体结论**：架构感知的轻量级分析建模能够有效揭示器件级评估遗漏的性能权衡，是早期 PIM DSE 的实用工具。

## 7. 优点

- **速度**：秒级评估，比 gem5 快 2–3 个数量级，使迭代式 DSE 成为可能。
- **统一性**：一个公式体系同时覆盖 PNM/PUM 和任务卸载/数据触发，模型表达力强。
- **架构感知**：显式建模主机–PIM 传输、阵列访问、设备编程延迟和容量分区，跨层因素进入同一框架。
- **验证扎实**：同时用真实商用 PIM 硬件（UPMEM）和大量周期精确仿真验证，可信度高。
- **可复现性**：源码和评估脚本开源。
- **实用洞察**：能从少量输入直接得出盈亏平衡点、Amdahl 上限、容量墙和技术选择等设计者关心的结论。

## 8. 不足与局限

- **不建模内存级并行（MLP）**：导致在乱序 CPU 和非规则访问模式（GraphBig）下系统性高估 PIM 开销；虽然趋势正确，但绝对误差可能较大。
- **传输模型简化**：UPMEM 案例中固定传输成本假设失效，必须用手工修正的随 DPU 数增长的传输模型才能复现实测行为，说明原始模型缺少对共享传输路径和调度开销的刻画。
- **容量模型粗糙**：仅用 `ceil(D_PIM/C_PIM)` 一阶乘数，忽略 bank 级并行、非均匀数据布局、以及部分容量可用的复杂情况。
- **数据触发验证粒度粗**：使用聚合 `t_PIM,mem` 而未分解 `tarray/tprog`，未充分验证展开式中的具体器件项。
- **实验对比不足**：未与其他分析模型（LogCA、Gables）在相同场景下进行定量对比，缺乏相对优越性的直接证据。
- **应用范围限制**：依赖“主机行为不随 PIM 设计变化”的假设，对主机端每次卸载都会改变指令流的应用（如动态调度、分支依赖卸载结果）可能不适用。
- **仅关注性能**：未包含能量模型，延展到性能-能量联合 DSE 需作为未来工作。
