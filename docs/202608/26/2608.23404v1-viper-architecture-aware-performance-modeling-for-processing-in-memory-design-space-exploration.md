## 摘要
处理入内存（PIM）有望通过在内存中或内存附近执行计算来减少数据移动开销，但其实际应用加速效果高度依赖设计。不可卸载的主机执行、主机与PIM之间的传输、有限的PIM容量以及设备编程延迟都可能限制端到端加速比，这使得快速早期设计空间探索（DSE）至关重要。然而，现有的PIM评估方法仍有局限：电路级和器件级工具无法捕获这些端到端PIM性能因素，而周期精确模拟对于迭代式DSE而言过于缓慢。为弥补这一空白，我们提出了VIPER，一个统一、轻量级且体系结构感知的PIM DSE性能评估框架。VIPER对主机执行进行一次性剖析，并将测得的主机行为与一个PIM感知的分析引擎相结合，该引擎在候选设计空间内扫描PIM侧参数。它通过捕获主机-PIM传输、阵列访问、内存内计算、设备编程延迟以及容量引起的分区，支持近内存处理（PNM）和使用内存处理（PUM）的任务卸载与数据触发执行模式，为迭代式DSE提供快速的体系结构感知性能估计，而无需重复进行周期精确模拟。我们针对商用UPMEM系统和超过400个周期精确的gem5配置对VIPER进行了验证。VIPER先验地预测了UPMEM的卸载决策和盈亏平衡区间，并通过精化的传输模型，在DPU扫描中捕获了实测的峰值-滚降行为，平均速度误差为12%（在256-DPU峰值之前误差为6%）。与gem5相比，VIPER的误差低于10%，同时将评估时间从数小时缩短至不到一分钟。针对UPMEM、ReRAM/FeFET交叉阵列和IMCRYPTO的案例研究表明，体系结构感知的DSE揭示了器件级评估无法捕捉的关键性能权衡。

## Abstract
Processing-in-Memory (PIM) promises to reduce data movement overhead by executing computation in or near memory, but its realized application speedup remains highly design-dependent. Non-offloadable host execution, host-PIM transfers, limited PIM capacity, and device programming latency can limit end-to-end speedup, making fast early-stage design-space exploration (DSE) essential. However, existing PIM evaluation methods remain limited: circuit- and device-level tools cannot capture these end-to-end PIM performance factors, while cycle-accurate simulation is too slow for iterative DSE. To address this gap, we present VIPER, a unified, lightweight, and architecture-aware performance evaluation framework for PIM DSE. VIPER profiles host execution once and combines the measured host behavior with a PIM-aware analytical engine that sweeps PIM-side parameters across candidate designs. It supports both Processing Near Memory (PNM) and Processing Using Memory (PUM) under task-offloading and data-triggered execution by capturing host-PIM transfer, array access, in-memory computation, device programming latency, and capacity-induced partitioning, providing rapid architecture-aware performance estimates for iterative DSE without repeated cycle-accurate simulation. We validate VIPER against a commercial UPMEM system and more than 400 cycle-accurate gem5 configurations. VIPER predicts the UPMEM offloading decision and break-even region a priori, and, with a refined transfer model, captures the measured peak-and-rolloff behavior with 12\% mean speedup error across the DPU sweep (6\% up to the 256-DPU peak). Against gem5, VIPER achieves less than 10\% error while reducing evaluation time from hours to under one minute. Case studies of UPMEM, ReRAM/FeFET crossbars, and IMCRYPTO show that architecture-aware DSE reveals key performance trade-offs that device-level evaluation misses.

## 1. 论文的核心问题与整体含义（研究动机和背景）

**核心问题**：如何在没有真实硬件或完整模拟器的情况下，快速且准确地评估一个 PIM（Processing-in-Memory）设计的端到端性能收益？

**背景与动机**：
- PIM 通过在内存中或内存附近执行计算来减少数据移动开销，但其实际加速效果高度依赖设计选择：不可卸载的主机执行、主机-PIM 数据传输、PIM 容量限制、NVM 器件编程延迟等因素都会显著影响端到端性能。
- 现有评估工具存在根本性缺陷：
  - **电路/器件级工具**（如 IMAC-Sim、Eva-CAM）：精度高但只覆盖阵列边界，无法捕捉主机交互、传输开销和容量约束；
  - **周期精确模拟器**（如 gem5-X、gem5-SALAM、PIMSim）：全面但单配置需 6–30 小时，迭代式 DSE 不可行；
  - **接口级模型**（如 LogCA、Gables）：速度快但将主机和内存系统抽象为平坦的接口成本，无法表达容量分区、编程延迟等 PIM 特有开销；
  - **应用级模拟器**（如 NeuroSim）：局限于特定领域。
- 现有工具没有一种能够同时满足：**快速**、**准确**、**架构感知**、**同时支持 PNM 与 PUM**。

**核心洞见**：PIM 不应被视为"主机附带的加速器"，而应被建模为**内存层次结构中的一个组件**——这样所有 PIM 相关成本（从器件物理到主机交互）都直接进入内存访问路径。

## 2. 论文提出的方法论

### 核心思想
- 基于经典 AMAT（Average Memory Access Time）模型，将 PIM 特有的时序项和容量项嵌入内存访问路径，建立统一的跨层分析性能模型。
- 利用 PIM 执行的一个结构性特性：**应用的主机侧行为不依赖于所挂载的 PIM 设计**。因此主机参数只需剖析一次，之后仅扫描 PIM 侧参数即可，将模拟从 DSE 循环中移除。

### 任务卸载模型（Task Offloading）
总执行时间 = CPU 执行时间 + PIM 执行时间：

```
T = I_CPU × (CPI_CPU,exec + m_CPU × AMAT_CPU) × CC_CPU
  + I_PIM × (CPI_PIM,exec + m_PIM × t_PIM,mem) × CC_PIM
```

### 数据触发模型（Data Triggering）
PIM 执行被内存访问事件自动触发，t_DRAM 被 t_PIM,mem 替换：

```
AMAT_PIM = t_L1 + m_L1 [t_L2 + m_L2 (t_L3 + m_L3 · t_PIM,mem)]
```

### PIM 时序模型
- **PNM + 任务卸载**：t_PIM,mem = (t_in + t_array + t_out) / CC_PIM
- **PUM + 任务卸载**：t_PIM,mem = (t_in + t_prog + t_out) / CC_PIM（无 t_array，但有编程延迟）
- **PNM + 数据触发**：t_PIM,mem = ⌈D_PIM/C_PIM⌉ × (t_in + t_array + t_comp + t_out) / CC_CPU
- **PUM + 数据触发**：t_PIM,mem = ⌈D_PIM/C_PIM⌉ × (t_in + t_prog + t_comp + t_out) / CC_CPU
- **容量分区模型**：m_PIM = ⌈D_PIM / C_PIM⌉，即工作集超出 PIM 容量时的调用次数倍增因子。

### VIPER 框架流程
1. **Profiling 阶段（一次）**：使用 Linux perf 收集硬件计数器，派生 CPU 侧固定参数：指令数、执行 CPI、内存访问率、AMAT、时钟周期。
2. **Sweeping 阶段（每设计点）**：设计者扫描 PIM 侧参数（指令数、计算效率、存储器延迟、容量、时钟周期），VIPER 在秒级内评估每个候选设计。

## 3. 实验设计

### 验证场景一：任务卸载验证（gem5-SALAM）
- **模拟平台**：单核 in-order ARM MinorCPU，默认 L1/L2，8GB DDR4-2400。
- **加速器**：GEMM 集群（LLVM-IR 建模），三个操作数 scratchpad，DMA 引擎。
- **基准**：单层 Llama2 transformer prefill（dim=128，hidden=256，8 heads，B=128）。
- **扫描参数**：GEMM tile 尺寸（8–256）、PIM 计算延迟 c（5–5000）、scratchpad 延迟 m（0–128），共 **6×7×8 = 336 个配置**。
- **对照**：VIPER 预测 vs gem5-SALAM 模拟。

### 验证场景二：数据触发验证（扩展 gem5-SALAM + perf）
- **配置**：11 种 PIM 配置（C1–C11），覆盖 SRAM/DRAM/HBM/NVM/存储级 PIM、in-order/OoO CPU、不同触发层级（L1 后/LLC 后/DRAM 内）。
- **基准**：SPEC2017（包括 462.libquantum、619.lbm_s、625.x264_s、638.imagick_s 等）和 GraphBig，共 12 个基准，GitHub 开发者社交网络数据集。
- **指标**：相对于无 PIM 基线的归一化延迟。

### 验证场景三：真实 PIM 系统验证（UPMEM）
- **系统**：2,560-DPU UPMEM 服务器（350 MHz，SDK 2025.1.0，Intel Xeon Silver 4215）。
- **工作负载**：单层 Llama2 prefill 的 8 个 matmul 全部卸载。
- **先验预测**：完全基于 perf 剖析 + 已发表的 UPMEM 参数（45 MOPS/DPU、2.5/2.0 GB/s 带宽、0.1 ms 启动开销）。

### 案例研究
1. **UPMEM（PNM）**：LLM 推理加速预测与实测对比。
2. **ReRAM/FeFET 交叉阵列（PUM）**：使用 DNN+NeuroSim（8-bit，22nm）模拟 8 层 DNN，对比内核级（kernel-only）与端到端速度。
3. **IMCRYPTO（PUM 数据触发）**：SRAM 内存内 AES-128 加密网关，在 SPEC2017 和 GraphBig 上评估 AMAT 代价。

## 6. 论文的主要结论与发现

1. **VIPER 对 gem5 的准确性**：任务卸载 336 点中 97% 预测在 ±10% 包络内；数据触发在 in-order CPU 上 MAE=0.114（约占全范围 2.4%），Pearson r=0.995（in-order）和 0.994（OoO）。
2. **对真实 UPMEM 硬件的验证**：
   - 先验预测可靠性：盈亏平衡点预测约 35 DPU，实测约 40–49 DPU；Amdahl 上限 6.57× 被正确预测。
   - **精化传输模型后**：峰值约 3.0×（预测）vs 2.46×（实测，256 DPU），12% 平均速度误差（峰值前 6%）。
   - 揭示了**最优 DPU 数量**现象：超过数百个 DPU 后增加处理单元反而降低端到端速度；原因在于共享主机传输路径使总传输时间随 DPU 数线性增长。
3. **对 XBA 交叉阵列的发现**：
   - 41–70× 的内核级加速转换为端到端只有至多 **2.96×**，主机不可卸载工作成为瓶颈；
   - **容量悬崖效应**：阵列稍小于工作集时，因重复分区和重新编程，性能反而远差于更小的阵列；
   - ReRAM/FeFET 的差别仅当编程延迟进入关键路径时才体现（批处理可掩盖，单查询场景则性能崩塌）。
4. **对 IMCRYPTO 的发现**：
   - 恒开内存内加密仅使 AMAT 增加 1.5%（均值）/ 6.2%（最坏），与 gem5 的差异在 0.2% 以内；
   - **技术筛选**：保持最坏情况 10% 预算需要 t_prog ≤ 21 周期：CMOS（6.2%）和 FeFET（9.8%）合格，RRAM（13.6%）和 PCM（25.0%）不合格。
5. **总体结论**：器件级评估无法揭示的关键性能权衡（Amdahl 天花板、容量墙、传输瓶颈、技术选择边界）只能通过架构感知的 DSE 获得。

## 7. 优点

1. **统一性**：一个模型同时支持 PNM/PUM × 任务卸载/数据触发四种组合，填补了现有工具覆盖面空白。
2. **速度**：每配置评估从 6–30 小时的 gem5 模拟压缩到 1 分钟以内，使数百点的迭代 DSE 成为可能。
3. **准确性**：与真实硬件和周期精确模拟的双重验证（<10% 平均误差）支撑了分析模型的有效性。
4. **先验预测能力**：仅凭主机剖析和公开参数即可在移植任何 DPU 代码之前预测 UPMEM 卸载决策和盈亏平衡区间。
5. **架构感知的洞察力**：揭示了器件级工具无法观察到的关键现象——最优 DPU 数量、容量悬崖、技术选择阈值。
6. **开源**：代码和评估脚本公开，可复现。

## 8. 不足与局限

1. **AMAT 顺序假设**：模型假设内存访问是顺序 stall 成本，无法捕捉内存级并行（MLP）。在 OoO CPU 和访问模式高度不规则的基准（如 GraphBig）下，VIPER 系统性高估归一化延迟。作者明确指出此为保守设计，但精确性受限。
2. **UPMEM 验证覆盖不足**：
   - 先验预测未能捕捉峰值-滚降行为，必须通过实测数据精化传输模型才能复现；这意味着只提升传输项为一次仿射函数。
   - 精化后仍有 12% 平均误差，中段 DPU 偏移（256 vs 570 DPU）和超过 512 DPU 的 1/N 缩放偏离未完全解释。
3. **数据触发验证使用了聚合延迟**：t_PIM,mem 作为单一值注入 gem5，没有分解为 t_array/t_prog 验证时序模型细节。
4. **案例规模有限**：UPMEM 和 XBA 案例仅使用单层/8 层小型 DNN，IMCRYPTO 仅评估单一 AES 设计；未涉及大规模 LLM、图分析等更复杂负载。
5. **未建模的效应**：未考虑 bank 级并行、内存调度策略、DMA 重叠等二阶效应；容量模型使用单一的 ⌈D/C⌉ 近似。
6. **验证偏重趋势而非绝对准确性**：数据触发验证采用归一化延迟指标，避免了绝对时间比较，但也削弱了对模型在某些绝对场景下可靠性的保证。
