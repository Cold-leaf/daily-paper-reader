## 摘要
内存处理（PIM）有望通过在内存中或内存附近执行计算来减少数据移动开销，但其实际应用加速仍然高度依赖于设计。不可卸载的主机执行、主机-PIM传输、有限的PIM容量和设备编程延迟可能限制端到端加速，因此快速早期设计空间探索（DSE）至关重要。然而，现有的PIM评估方法仍然有限：电路级和设备级工具无法捕获这些端到端的PIM性能因素，而周期精确模拟对于迭代式DSE来说太慢。为了解决这一差距，我们提出了VIPER，一个统一、轻量级且架构感知的PIM DSE性能评估框架。VIPER对主机执行进行一次剖析，并将测得的主机行为与一个PIM感知的分析引擎相结合，该引擎在候选设计间扫描PIM侧参数。它通过捕获主机-PIM传输、阵列访问、内存内计算、设备编程延迟和容量导致的划分，支持任务卸载和数据触发执行下的近内存处理（PNM）和内存内处理（PUM），无需重复的周期精确模拟即可为迭代式DSE提供快速的架构感知性能估计。我们针对商业UPMEM系统和400多个周期精确的gem5配置验证了VIPER。VIPER先验地预测UPMEM卸载决策和盈亏平衡区域，并通过精细的传输模型，捕获测得的峰值和滚降行为，在DPU扫描中平均加速误差为12%（在256-DPU峰值之前为6%）。与gem5相比，VIPER的误差小于10%，同时将评估时间从数小时缩短到不到一分钟。对UPMEM、ReRAM/FeFET交叉开关和IMCRYPTO的案例研究表明，架构感知的DSE揭示了设备级评估所遗漏的关键性能权衡。

## Abstract
Processing-in-Memory (PIM) promises to reduce data movement overhead by executing computation in or near memory, but its realized application speedup remains highly design-dependent. Non-offloadable host execution, host-PIM transfers, limited PIM capacity, and device programming latency can limit end-to-end speedup, making fast early-stage design-space exploration (DSE) essential. However, existing PIM evaluation methods remain limited: circuit- and device-level tools cannot capture these end-to-end PIM performance factors, while cycle-accurate simulation is too slow for iterative DSE. To address this gap, we present VIPER, a unified, lightweight, and architecture-aware performance evaluation framework for PIM DSE. VIPER profiles host execution once and combines the measured host behavior with a PIM-aware analytical engine that sweeps PIM-side parameters across candidate designs. It supports both Processing Near Memory (PNM) and Processing Using Memory (PUM) under task-offloading and data-triggered execution by capturing host-PIM transfer, array access, in-memory computation, device programming latency, and capacity-induced partitioning, providing rapid architecture-aware performance estimates for iterative DSE without repeated cycle-accurate simulation. We validate VIPER against a commercial UPMEM system and more than 400 cycle-accurate gem5 configurations. VIPER predicts the UPMEM offloading decision and break-even region a priori, and, with a refined transfer model, captures the measured peak-and-rolloff behavior with 12\% mean speedup error across the DPU sweep (6\% up to the 256-DPU peak). Against gem5, VIPER achieves less than 10\% error while reducing evaluation time from hours to under one minute. Case studies of UPMEM, ReRAM/FeFET crossbars, and IMCRYPTO show that architecture-aware DSE reveals key performance trade-offs that device-level evaluation misses.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：Processing-in-Memory（PIM）通过在内存中或内存附近执行计算，有望缓解传统冯·诺依曼架构中的数据搬运瓶颈（data movement bottleneck）。根据实现方式，PIM 分为两大类：
  - **PNM（Processing Near Memory）**：将处理单元放置在存储阵列旁（如 UPMEM、HBM-PIM），仍有阵列到计算单元的数据移动开销；
  - **PUM（Processing Using Memory）**：直接在存储单元内原位计算（如 RRAM/FeFET 交叉开关阵列），消除了内部数据传输但可能引入器件编程延迟。
- **核心矛盾**：PIM 的实际端到端加速高度依赖设计决策，但现有评估工具存在明显的"两难"困境：
  - 电路/器件级工具（如 IMAC-Sim、Eva-CAM）在阵列边界上精度高，但**无法捕获**主机-PIM 数据传输、非可卸载主机执行、容量不足导致的划分开销、器件编程延迟等端到端因素；
  - 周期精确全系统模拟器（如 gem5-SALAM、PIMSim）虽能全面建模，但**速度过慢**（每个配置需 6–30 小时），无法支撑迭代式设计空间探索（DSE）。
- **研究问题**：哪些设计参数决定 PIM 能否带来真正的性能收益？设计者如何在投片前快速量化这些参数？
- **核心论点**：论文用 GEMM 分块大小扫描和 NVM 编程延迟等案例证明，跨层参数交互（如容量悬崖效应、DPU 数量最优值、器件技术选型）在电路/器件层面完全不可见，**只有将 PIM 放入完整存储层次结构并用真实工作负载驱动，才能捕捉这些交互**。

## 2. 方法论：VIPER 框架

### 核心思想
- **关键洞察**：将 PIM 视为存储层次结构中的一个组件（而非传统的主机附属加速器），使器件物理、架构与主机交互的所有成本都直接进入内存访问路径。
- **建模基础**：在经典 **AMAT（Average Memory Access Time）** 模型上扩展 PIM 特定时序与容量项，得到统一的跨层 PIM 性能模型。
- **结构化优势**：应用的主机侧行为（指令混合、缓存行为、不可卸载工作）不依赖于所附着的 PIM 设计，因此**主机侧参数只需用 perf 剖析一次**，之后仅扫描 PIM 侧参数即可枚举整个设计空间，将模拟完全移出 DSE 循环。

### 技术细节与核心公式

**（1）任务卸载（Task Offloading）模型**——主机显式将计算委托给 PIM：

\[
T = I_{CPU} \times (CPI_{CPU,exec} + m_{CPU} \times AMAT_{CPU}) \times CC_{CPU} + I_{PIM} \times (CPI_{PIM,exec} + m_{PIM} \times t_{PIM,mem}) \times CC_{PIM}
\]

**（2）数据触发（Data-Triggered）模型**——PIM 由缓存未命中等内存事件自动激活，替代 AMAT 中的 \(t_{DRAM}\)：

\[
AMAT_{PIM} = t_{L1} + m_{L1}[t_{L2} + m_{L2}(t_{L3} + m_{L3} \cdot t_{PIM,mem})]
\]

**（3）PIM 时序模型**：
- **PNM 任务卸载**：\(t_{PIM,mem} = (t_{in} + t_{array} + t_{out}) / CC_{PIM}\)，包含主机→PIM 输入传输、阵列→处理单元数据移动、输出回传；
- **PUM 任务卸载**：\(t_{PIM,mem} = (t_{in} + t_{prog} + t_{out}) / CC_{PIM}\)，用 NVM 单元编程延迟 \(t_{prog}\) 替代 \(t_{array}\)（PUM 原位计算无需内部传输）；
- **数据触发模式**：增加计算项 \(t_{comp}\)，且时间按 CPU 时钟归一化（因 \(t_{PIM,mem}\) 直接替换 CPU 侧 AMAT 中的 \(t_{DRAM}\)）。

**（4）容量划分模型**：当工作集 \(D_{PIM}\) 超过 PIM 容量 \(C_{PIM}\) 时，任务被分割为多次调用：

\[
m_{PIM} = \lceil D_{PIM} / C_{PIM} \rceil
\]

### 框架流程
- **剖析阶段**：用 Linux perf 一次性收集 CPU 侧固定参数（退休指令数、执行 CPI、各级缓存未命中率、时钟周期等）；
- **扫描阶段**：设计者扫描 PIM 侧参数——任务卸载模式暴露指令数、计算效率、PIM 内存延迟、器件容量、时钟频率；数据触发模式仅需扫描 \(t_{PIM,mem}\) 与 \(C_{PIM}\) 两个参数。

### 充分性评估
- **优点**：覆盖面广——两种触发模型、两种 PIM 范式、多种存储技术（SRAM/DRAM/HBM/NVM/存储级）、多种 CPU 类型（in-order/OoO）、规则与不规则访存模式均有涉及；且包含真实硅片验证，这是纯模拟研究所不具备的。

## 6. 主要结论与发现

- **精度与速度**：与 gem5 对比，VIPER 平均误差 <10%，336 个任务卸载点中 97% 落在 ±10% 包络内；in-order 规则访问场景平均误差 4.4%，in-order 不规则访问 7.3%，OoO 规则 4.9%，OoO 不规则 5.5%。评估时间从数小时降至不足 1 分钟。
- **UPMEM 先验预测**：VIPER 在未移植任何 DPU 代码前就正确预测了 Amdahl 上限（6.57×）、盈亏平衡区间（预测 ~35 DPU，实测 40–49）和卸载决策；但 a-priori 模型高估了全服务器加速比（预测 4.3×，实测峰值 2.46×），原因是主机中介传输开销随 DPU 数量增长——修正单个传输参数后，VIPER 成功复现了"先升后降"的峰值-滚降行为，揭示 PNM 存在**最优 DPU 数**而非单调饱和。
- **XBA 交叉开关案例**：41–70× 的内核加速最终只转化为 ≤2.96× 的端到端加速（主机工作占主导）；当阵列容量略低于工作集需求时，性能出现**悬崖式下降**（单查询场景加速比跌至 0.04–0.1×）；ReRAM 与 FeFET 在容量充足时性能无差异，但容量受限时编程延迟差异（3×）进入关键路径——电路级模拟器无法发现这些现象。
- **IMCRYPTO 案例**：常开内存内加密使 AMAT 几何平均增加仅 1.5%（最坏情况 6.2%），VIPER 与 gem5 误差 <0.2%；编程延迟扫描显示，10% 最坏情况预算下 \(t_{prog} \lesssim 21\) 周期，CMOS 与 FeFET 合格，而 RRAM（13.6%）和 PCM（25.0%）不合格——器件技术选择决定了设计可行性。

## 7. 优点

- **统一建模框架**：单一 AMAT 基础上的公式同时覆盖 PNM/PUM 两大范式和任务卸载/数据触发两种触发模型，避免为不同范式维护独立工具链。
- **"剖析一次、扫描多次"的高效范式**：利用 PIM 设计中主机行为与 PIM 设计无关的结构特性，将模拟移出 DSE 循环，实现秒级评估。
- **跨层成本纳入**：将器件编程延迟、容量划分、主机-PIM 传输等电路/器件级工具看不见的因素变为模型中的一等公民。
- **验证层次完整**：既有 400+ 周期精确模拟验证，又有首个商业 PNM 系统（2,560-DPU UPMEM）上的真实硬件验证。
- **可复现性**：开源发布（GitHub），包含源码和评估脚本。
- **实际设计洞察**：识别出容量悬崖阈值、最优 DPU 数量、器件技术可行性筛选标准等投片前关键决策依据。

## 8. 不足与局限

- **AMAT 固有局限**：AMAT 建模顺序停顿成本，**不建模内存级并行（MLP）**，导致 OoO CPU 下系统性高估归一化延迟（不规则的 GraphBig 负载在高延迟配置下偏差最明显）。
- **UPMEM 传输模型精度不足**：a-priori 假设固定传输成本（1.40ms）被实测否定——实际传输随 DPU 数增长至 ~5.9ms。虽然单一参数修正能恢复预测精度，但说明初始模型对**主机中介传输的可扩展性**考虑不足。
- **容量模型二阶效应未建模**：容量划分使用 \(\lceil D/C \rceil\) 一阶近似，未精确处理 bank 级并行性和非均匀数据布局（论文将其留给设计者通过设置有效每分区容量来人工修正）。
- **精度指标口径**：数据触发验证仅比较**归一化趋势**而非绝对执行时间，可能掩盖系统性的绝对偏差。
- **能量维度缺失**：论文明确声明当前仅关注性能，功耗/能量建模留作未来工作——对早期设计决策而言，性能-能量联合优化是重要但未覆盖的方向。
- **应用范围有限**：案例研究集中于矩阵乘法、DNN 推理和 AES 加密，对更广泛的通用负载（如不规则图计算在高核数下的扩展性）覆盖不足。
