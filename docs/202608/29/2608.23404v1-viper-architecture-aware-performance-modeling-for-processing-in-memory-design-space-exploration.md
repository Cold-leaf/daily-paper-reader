## 摘要
内存内处理(PIM)通过在内存中或内存附近执行计算，有望降低数据移动开销，但其实现的应用加速仍然高度依赖于设计。不可卸载的主机执行、主机-PIM传输、有限的PIM容量以及设备编程延迟都可能限制端到端加速，这使得快速的早期设计空间探索(DSE)变得至关重要。然而，现有的PIM评估方法仍然有限：电路级和设备级工具无法捕获这些端到端的PIM性能因素，而周期精确仿真对于迭代式DSE来说又太慢了。为了弥补这一差距，我们提出了VIPER，一个统一、轻量级且架构感知的PIM DSE性能评估框架。VIPER对主机执行进行一次性能剖析，并将测得的主机行为与一个PIM感知的分析引擎相结合，该引擎在候选设计间扫描PIM侧参数。它通过捕获主机-PIM传输、阵列访问、内存内计算、设备编程延迟和容量引起的分区，支持任务卸载和数据触发执行下的近内存处理(PNM)和利用内存处理(PUM)，为迭代式DSE提供快速的架构感知性能估计，而无需重复进行周期精确仿真。我们针对商业UPMEM系统和400多个周期精确的gem5配置验证了VIPER。VIPER先验地预测了UPMEM的卸载决策和盈亏平衡区域，并通过精化的传输模型，在DPU扫描中捕捉到了实测的峰值-滚降行为，平均加速误差为12%（在256-DPU峰值之前为6%）。与gem5相比，VIPER的误差小于10%，同时将评估时间从数小时缩短至不到一分钟。对UPMEM、ReRAM/FeFET交叉阵列和IMCRYPTO的案例研究表明，架构感知的DSE揭示了设备级评估所遗漏的关键性能权衡。

## Abstract
Processing-in-Memory (PIM) promises to reduce data movement overhead by executing computation in or near memory, but its realized application speedup remains highly design-dependent. Non-offloadable host execution, host-PIM transfers, limited PIM capacity, and device programming latency can limit end-to-end speedup, making fast early-stage design-space exploration (DSE) essential. However, existing PIM evaluation methods remain limited: circuit- and device-level tools cannot capture these end-to-end PIM performance factors, while cycle-accurate simulation is too slow for iterative DSE. To address this gap, we present VIPER, a unified, lightweight, and architecture-aware performance evaluation framework for PIM DSE. VIPER profiles host execution once and combines the measured host behavior with a PIM-aware analytical engine that sweeps PIM-side parameters across candidate designs. It supports both Processing Near Memory (PNM) and Processing Using Memory (PUM) under task-offloading and data-triggered execution by capturing host-PIM transfer, array access, in-memory computation, device programming latency, and capacity-induced partitioning, providing rapid architecture-aware performance estimates for iterative DSE without repeated cycle-accurate simulation. We validate VIPER against a commercial UPMEM system and more than 400 cycle-accurate gem5 configurations. VIPER predicts the UPMEM offloading decision and break-even region a priori, and, with a refined transfer model, captures the measured peak-and-rolloff behavior with 12\% mean speedup error across the DPU sweep (6\% up to the 256-DPU peak). Against gem5, VIPER achieves less than 10\% error while reducing evaluation time from hours to under one minute. Case studies of UPMEM, ReRAM/FeFET crossbars, and IMCRYPTO show that architecture-aware DSE reveals key performance trade-offs that device-level evaluation misses.

## 2. 论文提出的方法论：核心思想、关键技术细节与流程

### 2.1 核心思想

**将 PIM 视为内存层次结构中的一个组件，而非传统的主机附加加速器。**

VIPER 基于经典的**平均内存访问时间（AMAT）** 公式，将 PIM 的开销直接嵌入内存访问路径中，使器件物理参数（如 NVM 编程延迟）、架构级参数（如传输带宽、容量）和执行级参数（如指令数、CPI）纳入同一个统一分析框架。

**关键结构洞察**：一个应用的主机侧行为（指令混合、缓存行为、不可卸载工作）**不依赖于外部 PIM 设计**，因此 CPU 侧参数只需剖析一次，PIM 侧参数则可自由扫描，从而将仿真从 DSE 循环中完全移除。

### 2.2 任务卸载模型（Task Offloading）

总执行时间（公式 2）：
```
T = ICPU × (CPICPU,exec + mCPU × AMATCPU) × CCCPU
    + IPIM × (CPIPIM,exec + mPIM × tPIM,mem) × CCPIM
```

PIM 内存访问时间 tPIM,mem 按范式分解：

- **PNM（近内存处理）**（公式 5）：
  ```
  tPIM,mem = (tin + tarray + tout) / CCPIM
  ```
  包含输入传输、数组到处理单元的数据移动、输出传输，并以 PIM 时钟周期归一化。

- **PUM（内存内处理）**（公式 7）：
  ```
  tPIM,mem = (tin + tprog + tout) / CCPIM
  ```
  消除 tarray，但引入 NVM 单元编程延迟 tprog。

- **容量分区因子**（公式 6）：
  ```
  mPIM = 1                    若 DPIM ≤ CPIM
       = ⌈DPIM / CPIM⌉       若 DPIM > CPIM
  ```

### 2.3 数据触发模型（Data Triggering）

PIM 执行由缓存未命中或 DRAM 访问等硬件事件自动触发，无需 CPU 显式指令。此时 PIM 延迟直接替换标准 AMAT 中的 DRAM 延迟（公式 3）：
```
AMATPIM = tL1 + mL1[tL2 + mL2(tL3 + mL3·tPIM,mem)]
```

- **PNM**（公式 8）：
  ```
  tPIM,mem = ⌈DPIM/CPIM⌉ × (tin + tarray + tcomp + tout) / CCCPU
  ```
- **PUM**（公式 9）：
  ```
  tPIM,mem = ⌈DPIM/CPIM⌉ × (tin + tprog + tcomp + tout) / CCCPU
  ```
  注意此处以 CPU 时钟周期归一化，因为 tPIM,mem 直接替换内存路径上的 tDRAM。

### 2.4 工作流程

1. **剖析阶段（Profiling）**：使用 Linux `perf` 硬件计数器，一次采集：
   - 退休指令数 ICPU；
   - 执行专用 CPI（通过层次化缓存模型扣除内存停顿周期）；
   - 每指令内存访问率 mCPU；
   - 各级缓存缺失率和命中延迟 → AMATCPU；
   - 时钟周期 CCCPU。
   
   CPU 侧参数全部固定，不再进入 DSE 循环。

2. **扫描阶段（Sweeping）**：设计者扫描 PIM 侧参数，按任务卸载或数据触发两条流程进行评估：
   - 任务卸载：IPIM、CPIPIM,exec、CCPIM、tPIM,mem、CPIM；
   - 数据触发：仅 tPIM,mem 和 CPIM。

3. **输出**：端到端执行时间 T、加速比、盈亏平衡点、Amdahl 天花板、对 tprog/tarray/CPIM 的敏感度等。

## 6. 论文的主要结论与发现

### 核心结论
1. **端到端加速受制于跨层因素**：主机上不可卸载的工作、CPU-PIM 数据传输的开销、PIM 容量不足引发的分区，以及 NVM 单元的编程延迟，共同决定了 PIM 设计的实际收益，而这些在电路/器件级无法观测。

2. **VIPER 达到高精度**：对 400+ gem5 配置均误差 <10%（任务卸载 97% 的点落入 ±10% 包络）；UPMEM 实机验证的 DPU 扫描均加速误差 12%（256-DPU 峰值前 6%）。

3. **评估提速显著**：从 gem5 的每配置 6–30 小时降低到 VIPER 的不到 1 分钟。

### 案例研究的具体发现
- **UPMEM 案例**：非可卸载主机工作设定 Amdahl 天花板（6.57×）；更关键的是，主机中介传输和每分派开销导致**存在最优 DPU 数量**（实测在 ~256 DPU 处峰值 2.46×，之后下降），而非单调饱和——这一行为在最初的固定传输模型下不可见，精化传输项后方可复现；
- **XBA 案例**：41–70× 的内核级加速在端到端最多只能带来 2.96×（受 3.05× Amdahl 天花板约束）；容量略小于工作集的阵列性能反而劣于远小于工作集的阵列（需反复分割重载）；单查询推理在容量不足时性能崩塌至 0.04–0.1×，而批量推理下仍保有 1.8–2.9×；
- **IMCRYPTO 案例**：始终开启的内存加密仅使 AMAT 平均增加 1.5%（最差 6.2%）；为保持在 10% 最差预算内需要 tprog ≲ 21 周期：CMOS（6.2%）和 FeFET（9.8%）合格，RRAM（13.6%）和 PCM（25.0%）不合格——同样的 PIM 设计在不同存储技术上的可行性截然不同。

## 7. 优点：方法或实验设计上的亮点

1. **统一的建模框架**：一个基于 AMAT 的公式同时覆盖 PNM/PUM 和任务卸载/数据触发两个维度，跨层成本（器件物理→架构→执行）不是拼凑而是从同一个模型中导出，优雅而简洁。

2. **"剖析一次，扫描多次"的巧妙设计**：利用 PIM 应用中 CPU 行为与 PIM 设计解耦的结构性属性，将仿真完全移出 DSE 循环。这是整个框架效率优势的根本来源。

3. **验证的多层次与互补性**：商业硬件（UPMEM，真实硅片）+ 周期精确仿真（400+ gem5 配置）+ 电路级仿真（NeuroSim）三足鼎立，兼顾真实性、广度和深度。在 UPMEM 上先验预测再实测的设计尤为严谨。

4. **诚实报告模型边界**：明确承认 AMAT 顺序停顿假设不建模 MLP，并定量报告 OoO 条件下的系统高估误差，不回避局限。

5. **真实设计洞察**：三个案例研究都揭示了电路级评估看不到的关键权衡（最优 DPU

数、容量悬崖、写延迟技术约束），证明了模型在真实设计决策中的指导价值。

## 8. 缺点与局限性：方法或实验设计上的不足

1. **顺序停顿假设的根本局限**：VIPER 基于 AMAT 公式隐含假定内存停顿严格串行化流水线，不建模多丢失（MLP/memory-level parallelism）。OoO CPU 场景下因此系统性高估 PIM 延迟的影响。论文虽诚实报告了这一误差，但并未提出修正方案。

2. **剖析流程依赖真实硬件**：CPU 侧参数需在真实 CPU 上用 `perf` 采集，意味着 VIPER 无法对尚未存在的 CPU 微架构做前瞻性探索；且 `perf` 剖析本身的噪声和 cache 建模误差会直接传播到最终预测。

3. **缺少组件级消融实验**：对 tPIM,mem 内部各项（tin/tarray/tprog/tcomp）的贡献度没有逐项验证，无法判断哪些项是主导误差来源。

4. **数据触发模型验证粒度偏粗**：使用聚合的 tPIM,mem 注入 gem5，未分解验证 tarray/tprog 等内部项，也未验证容量分区因子 mPIM 在数据触发模式下的单独行为。

5. **UPMEM 验证场景单一**：仅覆盖 Llama2 prefill 的单层 matmul 卸载（规则访问模式），未验证不规则工作负载（如稀疏、图计算）在真实 PIM 硬件上的预测精度。

6. **缺少对传输模型精化过程的详细描述**：UPMEM 案例中"固定传输模型不可见、精化后可见"的最优 DPU 数发现，是本文最有趣的结论之一，但论文未清晰交代初始模型与精化模型的差异以及精化的依据。

7. **容量分区假设简化**：工作集按整数倍分区，未考虑 PIM 内部跨分区数据依赖、跨 DPU 通信或数据重用的中间结果驻留问题。

## 9. 基于论文内容的设计结论与实用建议

1. **对 PIM 架构设计者**：
   - 不要以内核级加速作为设计目标，应以端到端加速为北极星；内核级 40–70× 加速在端到端往往只能兑现 2–3×。
   - NVM 编程延迟是 PUM 范式能否在实际系统中落地分的关键筛选条件——本案例中 tprog 必须 ≲ 21 周期才能守住 10% 性能预算，CMOS/FeFET 合格而 RRAM/PCM 不合格。
   - PIM 容量必须覆盖工作集，否则分区重载开销会导致性能悬崖；但容量"勉强够"比"大幅不够"更危险——分区重载次数与收益不成线性。

2. **对 PIM 应用开发者**：
   - 为不可卸载的主机部分做优化（降低 Amdahl 天花板）比追求更高的 PIM 内核速度更能撬动端到端性能。
   - 主机-PIM 数据传输的每分派开销会制造"最优 PIM 规模"而非单调扩展——需要以实际测量而非直觉决定 DPU 数量。

3. **对系统研究者**：
   - 在 PIM 设计的早期阶段，使用 VIPER 一类快速模型做粗粒度 DSE 筛选，仅对少数最有希望的配置跑周期精确仿真，可节省数天到数周的仿真时间。

## 10. 综合评价

VIPER 的学术贡献可总结为三点：

- **方法论创新**：将 PIM 从"附加加速器"还原为"内存层次的一个组件"，用 AMAT 这一成熟框架统一两大离散的 PIM 范式，使得跨层代价（器件物理 → 架构 → 系统 → 应用）可在同一模型中计算，而非拼接式估算。
- **工程效率突破**："剖析一次，扫描多次"的显式去耦策略，将 PIM 设计探索从每配置的小时级仿真降为秒级计算，这是该领域真正缺少的能力。
- **验证严谨性**：同时具备商业硬件的真实验证、周期精确仿真的广度覆盖、诚实报告模型边界三个品质，在同类工具中罕见。

主要短板在于数据触发模式的分解验证不足、OoO 场景的已知误差未修正、以及 UPMEM 实机验证的负载多样性有限。但这不影响其作为 PIM 快速 DSE 工具的代表性地位——论文的结论（端到端加速受挫于 Amdahl 天花板、容量和编程延迟）对 PIM 社区具有明确的设计指导意义。

**总体判断**：VIPER 是一个架构上优雅、验证上充分、结论上有实战参考价值的 PIM 建模与设计空间探索框架，填补了电路级模拟器与全系统模拟器之间的效率—精度空白，值得作为 PIM 早期设计评估的首选工具。
