## 摘要
处理进内存（PIM）有望通过在内或近内存执行计算来减少数据移动开销，但其实际应用加速仍高度依赖设计。不可卸载的主机执行、主机与PIM之间的传输、有限的PIM容量以及设备编程延迟可能限制端到端加速，因此快速的早期设计空间探索（DSE）至关重要。然而，现有的PIM评估方法仍然有限：电路级和设备级工具无法捕获这些端到端的PIM性能因素，而周期精确模拟对于迭代式DSE来说过于缓慢。为弥补这一差距，我们提出了VIPER，一个统一、轻量级且架构感知的PIM DSE性能评估框架。VIPER对主机执行进行一次性能剖析，并将测得的主机行为与PIM感知的分析引擎相结合，该引擎在候选设计间扫描PIM侧参数。它通过捕获主机与PIM间的传输、阵列访问、内存内计算、设备编程延迟以及容量引起的分区，支持近内存处理（PNM）和使用内存处理（PUM）在任务卸载和数据触发执行下的性能评估，为迭代式DSE提供快速的架构感知性能估计，无需重复的周期精确模拟。我们针对商用的UPMEM系统和超过400个周期精确的gem5配置验证了VIPER。VIPER能够先验地预测UPMEM的卸载决策和盈亏平衡区域，并且凭借精细化的传输模型，在DPU扫描中捕获了实测的峰值后下降行为，平均加速误差为12%（在256-DPU峰值前为6%）。与gem5相比，VIPER的误差低于10%，同时将评估时间从数小时缩短至不到一分钟。对UPMEM、ReRAM/FeFET交叉阵和IMCRYPTO的案例研究表明，架构感知的DSE揭示了设备级评估所遗漏的关键性能权衡。

## Abstract
Processing-in-Memory (PIM) promises to reduce data movement overhead by executing computation in or near memory, but its realized application speedup remains highly design-dependent. Non-offloadable host execution, host-PIM transfers, limited PIM capacity, and device programming latency can limit end-to-end speedup, making fast early-stage design-space exploration (DSE) essential. However, existing PIM evaluation methods remain limited: circuit- and device-level tools cannot capture these end-to-end PIM performance factors, while cycle-accurate simulation is too slow for iterative DSE. To address this gap, we present VIPER, a unified, lightweight, and architecture-aware performance evaluation framework for PIM DSE. VIPER profiles host execution once and combines the measured host behavior with a PIM-aware analytical engine that sweeps PIM-side parameters across candidate designs. It supports both Processing Near Memory (PNM) and Processing Using Memory (PUM) under task-offloading and data-triggered execution by capturing host-PIM transfer, array access, in-memory computation, device programming latency, and capacity-induced partitioning, providing rapid architecture-aware performance estimates for iterative DSE without repeated cycle-accurate simulation. We validate VIPER against a commercial UPMEM system and more than 400 cycle-accurate gem5 configurations. VIPER predicts the UPMEM offloading decision and break-even region a priori, and, with a refined transfer model, captures the measured peak-and-rolloff behavior with 12\% mean speedup error across the DPU sweep (6\% up to the 256-DPU peak). Against gem5, VIPER achieves less than 10\% error while reducing evaluation time from hours to under one minute. Case studies of UPMEM, ReRAM/FeFET crossbars, and IMCRYPTO show that architecture-aware DSE reveals key performance trade-offs that device-level evaluation misses.

- **背景**：Processing-in-Memory（PIM）通过在内存中或内存旁执行计算，有望缓解数据移动瓶颈。但其实际端到端加速效果高度依赖体系结构设计，受多种跨层因素制约，包括：
  - 不可卸载的主机执行（非 PIM 部分）
  - 主机与 PIM 之间的数据传输开销
  - PIM 设备容量有限导致的多次分区与重载
  - NVM 器件的编程延迟（如 RRAM、FeFET 等比读慢 10–50 倍）
- **核心问题**：在 PIM 设计投入硅片之前，设计师需要回答体系结构级问题：应配置多少容量？选择哪种存储技术？多少个处理单元才是最优？如何量化这些设计参数对端到端性能的影响？
- **现有工具缺陷**：
  - 电路/设备级工具（如 IMAC-Sim、Eva-CAM）只关注阵列边界，无法建模主机交互、数据传输、容量限制等端到端因素。
  - 周期精确模拟器（如 gem5-X、gem5-SALAM、PIMSim）虽然全面，但每个配置需要 6–30 小时，难以支撑迭代式设计空间探索。
  - 应用级模拟器（如 NeuroSim、MNSIM）局限于特定领域；内存系统模拟器（如 Ramulator、DRAMsim3）忽略主机执行且对 PUM 支持有限。
- **论文主张**：需要一个快速、准确、架构感知的分析模型，能够同时覆盖 PNM 与 PUM，并支持任务卸载与数据触发两种执行模型，使设计师在无硬件和仿真器的情况下即可进行大规模 DSE。

## 2. 方法论：核心思想、关键技术细节与流程

### 核心思想
- **将 PIM 视为内存层次结构的一部分**，而不是一个独立的主机附加加速器。这样，PIM 的所有成本（设备物理延迟、阵列访问、主机交互、容量分区）都会直接进入内存访问路径。
- **基于经典 AMAT（Average Memory Access Time）模型进行扩展**，加入 PIM 特定的时序项和容量项，从而在不进行周期精确模拟的情况下估计端到端性能。
- **一次剖析，多次扫描**：任意应用的 CPU 侧行为（指令混合、缓存行为、不可卸载工作）与所连接的 PIM 设计无关，因此只需用 Linux perf 剖析一次，固定 CPU 侧参数，然后扫描 PIM 侧参数即可完成 DSE。

### 关键技术细节

#### 任务卸载模型（Task Offloading）
- 总执行时间 = CPU 执行时间 + PIM 执行时间：
  \[
  T = I_{CPU}(CPI_{CPU,exec}+ m_{CPU}\cdot AMAT_{CPU})\cdot CC_{CPU} + I_{PIM}(CPI_{PIM,exec}+ m_{PIM}\cdot t_{PIM,mem})\cdot CC_{PIM}
  \]
- \(t_{PIM,mem}\) 进一步拆分为：
  - **PNM**：\(t_{PIM,mem} = (t_{in}+t_{array}+t_{out})/CC_{PIM}\)
  - **PUM**：\(t_{PIM,mem} = (t_{in}+t_{prog}+t_{out})/CC_{PIM}\)
- 容量分区：当工作集超过容量时，\(m_{PIM} = \lceil D_{PIM}/C_{PIM}\rceil\)。

#### 数据触发模型（Data Triggering）
- PIM 位于内存关键路径上，\(t_{DRAM}\) 被替换为 \(t_{PIM,mem}\)：
  \[
  AMAT_{PIM} = t_{L1}+m_{L1}[t_{L2}+m_{L2}(t_{L3}+m_{L3}\cdot t_{PIM,mem})]
  \]
- PNM：  
  \[
  t_{PIM,mem} = \lceil D_{PIM}/C_{PIM}\rceil \times (t_{in}+t_{array}+t_{comp}+t_{out})/CC_{CPU}
  \]
- PUM：  
  \[
  t_{PIM,mem} = \lceil D_{PIM}/C_{PIM}\rceil \times (t_{in}+t_{prog}+t_{comp}+t_{out})/CC_{CPU}
  \]

#### VIPER 流程
1. **剖析阶段**：通过 Linux perf 获取指令数、周期数、各级缓存缺失率等，计算 CPI、内存访问率、AMAT 和时钟周期。
2. **扫描阶段**：
   - 任务卸载：设计师扫描 \(I_{PIM}\)、\(CPI_{PIM,exec}\)、\(CC_{PIM}\)、\(t_{PIM,mem}\)、\(C_{PIM}\)。
   - 数据触发：仅扫描 \(t_{PIM,mem}\) 和 \(C_{PIM}\)，因为无卸载决策。
3. **输出**：端到端执行时间、加速比、盈亏平衡点、Amdahl 上限、容量墙阈值等技术指标。

## 6. 主要结论与发现

- **VIPER 准确且高效**：
  - 与 gem5 相比，任务卸载模型在 336 个配置中 97.0% 落在 ±10% 误差带内，平均误差低于 10%。
  - 数据触发模型：in-order CPU 归一化延迟 Pearson 相关 r=0.995，MAE=0.114；OoO CPU 相关 r=0.994，但存在系统性高估（因忽略 MLP）。均能正确预测容量墙行为。
  - 评估时间从 6–30 小时/配置缩短到 <1 分钟。
- **UPMEM 案例**：
  - VIPER 先验预测了 Amdahl 上限（6.57×）、盈亏平衡点（约 35 DPU，实测 40–49）和卸载决策。
  - 固定传输模型预测单调上升，但实测为“峰值后下降”（峰值约 2.46×@256 DPU，2,560 DPU 时降至 1.75×）。通过将传输项建模为随 DPU 数线性增长（1.82+0.00168N ms），VIPER 成功复现峰值-下降行为（预测峰值约 3.0×@570 DPU）。
  - 关键见解：对 PNM 加速器，非卸载主机工作设定 Amdahl 天花板；但实际限制更紧——主机介导的传输和分发开销导致最优 DPU 数存在，而非单调饱和。
- **XBA 案例**：
  - 电路级 41–70× 的 kernel 加速，端到端最多只能带来 2.96×（因主机工作主导）。
  - 容量不足时，单查询推理严重崩溃（加速比降到 0.04–0.1×），而批量推理仍能保持 1.8–2.9×。
  - ReRAM 与 FeFET 在编程延迟上的差异（0.1/0.3 μs）只在编程进入关键路径时显现，电路级模拟器（NeuroSim）无法看到。
- **IMCRYPTO 案例**：
  - 数据触发式内存内加密仅增加 1.5% 平均 AMAT（最坏情况 6.2%，462.libquantum）。
  - 扫描编程延迟发现：若要保证最坏情况开销 <10%，需 \(t_{prog} \lesssim 21\) cycles；CMOS（6.2%）和 FeFET（9.8%）合格，RRAM（13.6%）和 PCM（25.0%）不合格。
  - 说明设备技术选择会决定同一 PIM 设计的可行性。

## 7. 优点

- **填补空白**：首个统一支持 PNM 和 PUM、任务卸载和数据触发、快速且架构感知的 PIM DSE 框架。
- **模型简单但有效**：基于 AMAT 的扩展天然契合 PIM 在内存层级中的位置，每项成本都有明确的物理含义和独立可解析的参数（传输、阵列访问、编程、容量）。
- **一次剖析、全局扫描**：利用 CPU 行为与 PIM 设计无关的观察，将仿真从 DSE 循环中移除，高效支持数百个设计点。
- **验证扎实**：除 gem5 400+ 配置外，还使用真实商用硬件 UPMEM 验证先验预测，增强了结果的可信度。
- **实用性强**：公开源代码，提供完整 DSE 流程（剖析→扫描→输出），能够揭示设备级评估遗漏的“悬崖/坡度”效应（容量墙、峰值后下降、技术差异导致的可行性差异）。
- **对 MLP 的假设合理**：承认未建模 MLP，但在 in-order 和 OoO 下均保持趋势准确，且 OoO 误差方向可预测（系统性高估）。

## 8. 不足与局限

- **MLP / 并行性忽略**：模型假设顺序停顿成本，不考虑内存级并行性和 PIM 内部多个 bank 或通道的并发。OoO CPU 下预测系统性地高估延迟（尤其 GraphBig 不规则访问），误差可达 5.5–7.3%。
- **传输模型初始假设简化**：UPMEM 案例中最初的固定传输假设与实测不符（实际传输随 DPU 数增长），需要人工细化后才准确。这说明模型对某些系统级开销（描述符设置、同步、共享传输路径）缺乏先验建模能力。
- **容量分区模型粗糙**：使用简单的 \(\lceil D/C \rceil\) 乘子，忽略了非均匀数据布局、bank 级并行和负载均衡等二阶效应（论文承认这一点）。
- **数据触发验证的基准数量有限**：仅 12 个基准（SPEC2017 + GraphBig 各一个数据集），且 OoO 下 GraphBig 误差较大，可能影响结论的普适性。
- **缺乏能量建模**：只关注性能（时间），未包含能耗项，对 PIM 设计（尤其 NVM）的能效评估不足（论文将能量扩展列为未来工作）。
- **CPU 侧参数依赖硬件计数器**：使用 Linux perf 和默认缓存延迟（tL3=10, tDRAM=100），如果目标主机与剖析主机差异较大，固定参数可能带来偏差。
- **未与其他解析模型（如 LogCA、Gables）做定量对比**：论文只比较了 gem5 和硬件，没有说明 VIPER 相比 LogCA 等模型在精度上的优势有多大。
- **应用场景局限**：案例研究集中在 LLM 推理、DNN 和 AES，未覆盖更多样化的 PIM 工作负载（如图处理、数据库、稀疏计算）。
