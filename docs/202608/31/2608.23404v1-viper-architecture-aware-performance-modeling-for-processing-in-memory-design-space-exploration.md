## 摘要
处理中存储器（PIM）有望通过在存储器内部或附近执行计算来减少数据移动开销，但其实际应用加速效果仍然高度依赖于设计。不可卸载的主机执行、主机与PIM之间的传输、有限的PIM容量以及设备编程延迟可能会限制端到端加速，因此快速的前期设计空间探索（DSE）至关重要。然而，现有的PIM评估方法仍然有限：电路级和器件级工具无法捕捉这些端到端PIM性能因素，而周期精确仿真对于迭代式DSE来说太慢。为解决这一差距，我们提出了VIPER，一个用于PIM DSE的统一、轻量级且架构感知的性能评估框架。VIPER对主机执行进行一次分析，并将测得的主机行为与一个PIM感知的分析引擎相结合，该引擎在候选设计间扫描PIM侧参数。它通过捕捉主机-PIM传输、阵列访问、存储器内计算、器件编程延迟以及容量引起的分区，在任务卸载和数据触发执行下支持近存储器处理（PNM）和使用存储器处理（PUM），无需重复的周期精确仿真即可为迭代式DSE提供快速的架构感知性能估计。我们针对商业UPMEM系统和超过400个周期精确的gem5配置验证了VIPER。VIPER先验地预测了UPMEM的卸载决策和盈亏平衡区域，并且通过改进的传输模型，捕捉了测得的峰值和滚降行为，在DPU扫描中平均速度误差为12%（在256-DPU峰值前为6%）。对比gem5，VIPER实现了低于10%的误差，同时将评估时间从数小时缩短到一分钟以内。对UPMEM、ReRAM/FeFET交叉阵列和IMCRYPTO的案例研究表明，架构感知的DSE揭示了器件级评估所忽略的关键性能权衡。

## Abstract
Processing-in-Memory (PIM) promises to reduce data movement overhead by executing computation in or near memory, but its realized application speedup remains highly design-dependent. Non-offloadable host execution, host-PIM transfers, limited PIM capacity, and device programming latency can limit end-to-end speedup, making fast early-stage design-space exploration (DSE) essential. However, existing PIM evaluation methods remain limited: circuit- and device-level tools cannot capture these end-to-end PIM performance factors, while cycle-accurate simulation is too slow for iterative DSE. To address this gap, we present VIPER, a unified, lightweight, and architecture-aware performance evaluation framework for PIM DSE. VIPER profiles host execution once and combines the measured host behavior with a PIM-aware analytical engine that sweeps PIM-side parameters across candidate designs. It supports both Processing Near Memory (PNM) and Processing Using Memory (PUM) under task-offloading and data-triggered execution by capturing host-PIM transfer, array access, in-memory computation, device programming latency, and capacity-induced partitioning, providing rapid architecture-aware performance estimates for iterative DSE without repeated cycle-accurate simulation. We validate VIPER against a commercial UPMEM system and more than 400 cycle-accurate gem5 configurations. VIPER predicts the UPMEM offloading decision and break-even region a priori, and, with a refined transfer model, captures the measured peak-and-rolloff behavior with 12\% mean speedup error across the DPU sweep (6\% up to the 256-DPU peak). Against gem5, VIPER achieves less than 10\% error while reducing evaluation time from hours to under one minute. Case studies of UPMEM, ReRAM/FeFET crossbars, and IMCRYPTO show that architecture-aware DSE reveals key performance trade-offs that device-level evaluation misses.

## 1. 论文的核心问题与整体含义（研究动机和背景）

- **背景**：处理中存储器（Processing-in-Memory, PIM）通过在存储器内部或附近执行计算，有望缓解传统冯·诺依曼架构中的数据移动瓶颈。但实际应用中，PIM 能带来的端到端加速高度依赖具体设计选择。
- **核心问题**：PIM 设计在流片前，架构师需要回答一系列架构级问题，例如：
  - 芯片上应提供多少容量？容量不足的代价是什么？
  - 哪种存储技术最适合承载计算？（非易失存储器编程比读取慢 10–50 倍）
  - 多少个处理单元才能抵消主机侧数据移动的开销？
- **现有评估工具的矛盾**：
  - 电路/器件级工具（如 IMAC-Sim、Eva-CAM）：精确但只覆盖阵列边界，无法反映主机交互、数据搬运、容量约束等端到端因素。
  - 周期精确全系统模拟器（如 gem5-X、gem5-SALAM、PIMSim）：能建模完整系统，但每个配置需要 6–30 小时，不适合迭代式设计空间探索（DSE）。
  - 接口级模型（如 LogCA、Gables）：速度快但将主机和存储系统简化为平面接口成本，无法建模容量分区、编程延迟等 PIM 特性。
- **核心主张**：早期 PIM DSE 必须“架构感知”——需要将 PIM 放入完整存储层次结构、由真实工作负载驱动，才能捕捉跨层的性能权衡。论文基于经典的 AMAT（平均内存访问时间）模型，提出 VIPER 框架。

## 2. 论文提出的方法论：核心思想、关键技术细节与流程

- **核心思想**：将 PIM 视为存储层次结构中的一个组件，而不是传统的“主机附加加速器”。这样，从器件物理到主机交互的所有 PIM 成本都直接进入内存访问路径，从而自然融入 AMAT 框架。
- **关键结构**：将程序执行时间分为主机（CPU）项与 PIM 项：
  - 主机侧参数通过一次 `perf` 剖析固定下来（指令数、CPI、缓存失效率、时钟周期等）；
  - PIM 侧参数由设计者扫描（传输延迟、计算延迟、容量、时钟频率等）。
  - 利用“应用的主机行为不依赖 PIM 设计”这一结构特性，去除仿真循环。
- **统一模型涵盖两种执行触发模型**：
  - **任务卸载（Task Offloading）**：CPU 显式将任务分派给 PIM，同步等待完成。总执行时间为 CPU 执行时间与 PIM 执行时间之和。
  - **数据触发（Data Triggering）**：PIM 由硬件存储事件（如缓存未命中）自动激活，处于关键内存访问路径上。模型用 PIM 延迟替换标准 AMAT 中的 DRAM 延迟。
- **PIM 时序模型的关键组件**：
  - `t_in`：主机到 PIM 的数据输入传输时间
  - `t_array`：存储阵列到处理单元的数据移动时间（PNM 特有）
  - `t_comp`：PIM 上的计算时间
  - `t_prog`：NVM 单元编程延迟（PUM 特有，如 RRAM/FeFET 的物理写入时间）
  - `t_out`：PIM 到主机的输出传输时间
  - `m_PIM = ceil(D_PIM / C_PIM)`：容量分区倍数，当工作集超过 PIM 容量时产生
- **PNM 与 PUM 的差异体现在模型项上**：
  - PNM：`t_PIM_mem = t_in + t_array + t_out`（存在阵列到处理单元的数据移动）
  - PUM：`t_PIM_mem = t_in + t_prog + t_out`（消除阵列内部搬运，但引入 NVM 编程延迟）
- **VIPER 框架流程**：
  1. **剖析阶段**：用 Linux `perf` 收集 CPU 侧数据（指令数、缓存命中率、周期数等），计算出 CPI_exec、内存访问率、AMAT、时钟周期。
  2. **扫描阶段**：设计者扫描 PIM 侧参数，利用公式计算端到端执行时间，快速评估数百个设计点。
- **核心公式**（以任务卸载为例）：

  ```
  T = I_CPU × (CPI_CPU_exec + m_CPU × AMAT_CPU) × CC_CPU
      + I_PIM × (CPI_PIM_exec + m_PIM × t_PIM_mem) × CC_PIM
  ```

## 6. 论文的主要结论与发现

- **VIPER 精度**：
  - 对 336 个任务卸载 gem5 配置，97% 的预测落在 ±10% 误差带内；整体平均误差 <10%。
  - 数据触发验证中，VIPER 对 in-order 规则的 SPEC 基准平均误差 4.4%，in-order 不规则 GraphBig 为 7.3%，OoO 规则为 4.9%，OoO 不规则为 5.5%。Pearson 相关系数超过 0.99。
  - UPMEM 案例：VIPER 先验准确预测了盈亏平衡 DPU 数（预测 35，实测 40–49）与 Amdahl 天花板（6.57×）；修正主机传输模型后可捕捉峰-滚降行为，速度误差 12%（峰值前 6%）。
- **架构级洞察**：
  - **设备级快≠端到端快**：一个 41–70× 的 PIM 内核，端到端最多只能带来 2.96× 加速，因为不可卸载的主机工作占主导。
  - **容量悬崖**：阵列容量略小于工作负载时，性能严格差于远小于它的阵列（需要反复分区重载）。单查询推理模式下，低于驻留阈值时加速比从 ~2.9× 跌至 0.04–0.1×（即性能反而比 CPU 慢）。
  - **PIM 数量存在最优值**：UPMEM 中，超过约数百个 DPU 后继续增加处理单元反而降低端到端加速，因为主机介导的传输与调度开销增长。
  - **技术选择取决于关键路径**：同一 AES 加速器，CMOS 和 FeFET 满足 10% 最坏情况开销预算，而 RRAM（13.6%）和 PCM（25.0%）不合格——这一结论无法从版图后数值直接得出。
- **总体结论**：VIPER 提供了快速、架构感知的 PIM DSE 途径，可在流片前揭示器件级评估遗漏的性能权衡，从而指导容量配置、处理单元数量和存储技术选择。

## 7. 优点：方法与实验设计亮点

- **模型统一性**：基于 AMAT 的单一公式同时覆盖 PNM/PUM 与任务卸载/数据触发，避免了为每种范式单独建模。
- **速度-精度平衡**：利用“主机行为不依赖 PIM 设计”的结构特性，一次剖析 + 参数扫描即可完成 DSE，将评估时间从小时级降至分钟级，同时保持 <10% 误差。
- **先验预测能力**：仅从公开的 UPMEM 参数和主机剖析数据，在未编写任何 DPU 代码时预测了卸载决策与盈亏平衡点。
- **真实硬件验证**：在商业 UPMEM 系统上验证，增加了结果的可信度。
- **多维度实验覆盖**：包含不同 CPU（in-order/OoO）、不同存储技术（SRAM/DRAM/HBM/NVM/存储级）、不同访问模式（规则/不规则）、不同容量与延迟组合。
- **开源**：代码和评估脚本公开，便于复现和扩展。
- **发现反直觉现象**：如容量悬崖、最优 DPU 数、技术依赖的可行性等，展示了架构感知建模的价值。
- **对模型局限有清醒认知**：明确承认不建模内存级并行（MLP），并量化了 OoO 下的高估误差，分析路径透明。

## 8. 不足与局限

- **MLP / 乱序执行建模缺失**：VIPER 假设顺序阻塞式内存访问，无法捕捉乱序 CPU 中多个未完成请求的重叠。虽然趋势方向仍正确，但 OoO 场景下系统性地高估延迟（尤其是不规则访问的 GraphBig 基准）。
- **真实硬件验证范围窄**：仅验证了 UPMEM（PNM 任务卸载）一种真实 PIM 系统，且只使用了 Llama2 prefill 一个应用。PUM 的真实硬件（如 ReRAM/FeFET 芯片）未涉及。
- **容量模型简化**：使用 `ceil(D/C)` 乘数近似容量分区开销，未建模 bank 级并行、非均匀数据布局、跨分区依赖等二阶效应。
- **数据触发验证粒度粗**：验证中只使用单一聚合延迟，未分别分解并验证 t_array/t_prog/t_comp 的贡献。
- **传输模型需要人工修正**：UPMEM 案例中，固定传输成本假设（1.40 ms）与实际硬件测量出入较大，需要将传输模型修正为随 DPU 数增长的仿射函数才能匹配峰-滚降行为。这意味着原始模型对“主机介导的聚合传输开销随处理单元数增长”这一现象缺乏先验捕捉能力。
- **基准集规模有限**：虽然 gem5 配置数超过 400，但应用种类相对受限（Llama2 变体、SPEC2017 子集、GraphBig 一个数据集），未涵盖更广泛的工作负载（如数据库、稀疏线性代数、图神经网络训练等）。
- **未纳入能耗模型**：论文明确说明只考虑性能，每访问能耗项留作未来工作。对于 PIM（特别是 NVM）来说，能耗/热是重要设计约束，缺少此项会限制 DSE 的完整性。
- **可能的应用限制**：分析模型依赖 `perf` 剖析的准确性，对不可准确卸载到 PIM 的复杂控制流任务（如不规则递归、动态分支密集代码）的适用性未深入探讨。
