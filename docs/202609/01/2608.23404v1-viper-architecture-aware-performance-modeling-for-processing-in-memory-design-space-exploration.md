## 摘要
内存内处理（PIM）有望通过在内存中或内存附近执行计算来减少数据移动开销，但其实际应用加速效果高度依赖设计。不可卸载的主机执行、主机-PIM传输、有限的PIM容量以及设备编程延迟可能限制端到端加速，这使得快速早期设计空间探索（DSE）至关重要。然而，现有的PIM评估方法仍然有限：电路级和设备级工具无法捕获这些端到端PIM性能因素，而周期精确模拟对于迭代DSE来说太慢。为了解决这一差距，我们提出了VIPER，一个统一、轻量级且架构感知的PIM DSE性能评估框架。VIPER对主机执行进行一次剖析，并将测得的主机行为与一个PIM感知的分析引擎相结合，该引擎在候选设计间扫描PIM侧参数。它通过捕获主机-PIM传输、阵列访问、内存内计算、设备编程延迟和容量引起的分区，支持任务卸载和数据触发执行下的近内存处理（PNM）和内存内处理（PUM），为迭代DSE提供快速的架构感知性能估计，而无需重复的周期精确模拟。我们针对商业UPMEM系统和超过400个周期精确的gem5配置验证了VIPER。VIPER预先预测UPMEM卸载决策和盈亏平衡区域，并通过精细的传输模型，捕获测得的峰值和滚降行为，在DPU扫描范围内平均加速误差为12%（直至256-DPU峰值时为6%）。与gem5相比，VIPER实现不到10%的误差，同时将评估时间从数小时缩短到一分钟以内。对UPMEM、ReRAM/FeFET交叉开关和IMCRYPTO的案例研究表明，架构感知DSE揭示了设备级评估遗漏的关键性能权衡。

## Abstract
Processing-in-Memory (PIM) promises to reduce data movement overhead by executing computation in or near memory, but its realized application speedup remains highly design-dependent. Non-offloadable host execution, host-PIM transfers, limited PIM capacity, and device programming latency can limit end-to-end speedup, making fast early-stage design-space exploration (DSE) essential. However, existing PIM evaluation methods remain limited: circuit- and device-level tools cannot capture these end-to-end PIM performance factors, while cycle-accurate simulation is too slow for iterative DSE. To address this gap, we present VIPER, a unified, lightweight, and architecture-aware performance evaluation framework for PIM DSE. VIPER profiles host execution once and combines the measured host behavior with a PIM-aware analytical engine that sweeps PIM-side parameters across candidate designs. It supports both Processing Near Memory (PNM) and Processing Using Memory (PUM) under task-offloading and data-triggered execution by capturing host-PIM transfer, array access, in-memory computation, device programming latency, and capacity-induced partitioning, providing rapid architecture-aware performance estimates for iterative DSE without repeated cycle-accurate simulation. We validate VIPER against a commercial UPMEM system and more than 400 cycle-accurate gem5 configurations. VIPER predicts the UPMEM offloading decision and break-even region a priori, and, with a refined transfer model, captures the measured peak-and-rolloff behavior with 12\% mean speedup error across the DPU sweep (6\% up to the 256-DPU peak). Against gem5, VIPER achieves less than 10\% error while reducing evaluation time from hours to under one minute. Case studies of UPMEM, ReRAM/FeFET crossbars, and IMCRYPTO show that architecture-aware DSE reveals key performance trade-offs that device-level evaluation misses.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：处理进内存（PIM）通过在内存中或内存附近执行计算，有望显著减少数据搬运开销。但实际应用能获得多少端到端加速，高度依赖于具体架构设计。
- **核心问题**：早期设计者面临的关键问题是——哪些设计参数决定了 PIM 能否带来真实性能收益？如何在流片前快速量化这些收益？
- **现存工具的矛盾**：
  - 电路/器件级工具（IMAC-Sim、EvaCAM 等）只能评估阵列边界内的性能，无法捕捉主机-PIM 传输、容量不足导致的分区、NVM 编程延迟等端到端因素；
  - 周期精确模拟器（gem5 系列、PIMSim 等）准确但每个配置需要 6–30 小时，难以支撑迭代式设计空间探索；
  - 应用级模拟器（NeuroSim、MNSIM 等）局限于特定领域；内存系统模拟器（Ramulator 等）又缺乏主机执行与 PUM 支持。
- **论文含义**：VIPER 提出了一种轻量级、架构感知的分析性性能评估框架，将 PIM 视为内存层次结构中的一部分而非独立加速器，从而在数秒内完成对数百个设计点的扫描，填补了“快速”与“架构级准确”之间的空白。

## 2. 方法论

### 核心思想
- 将 PIM 建模为**内存访问路径上的组件**，基于经典 AMAT（平均内存访问时间）公式扩展出跨层 PIM 性能模型。
- 关键洞察：应用的主机侧行为（指令混合、缓存行为、不可卸载工作）与具体 PIM 设计无关，因此**只需对主机执行剖析一次**，之后所有 PIM 设计点只需改变 PIM 侧参数即可快速评估。

### 模型组成
- **任务卸载模型**（Task Offloading）：总执行时间 = CPU 执行时间 + PIM 执行时间。CPU 侧用标准 AMAT 描述；PIM 侧包括指令数、CPI、PIM 内存延迟与容量分区倍数。
- **数据触发模型**（Data Triggering）：当触发事件发生时，将标准 AMAT 中的 DRAM 延迟替换为 PIM 内存延迟，直接计算 PIM 感知的 AMAT 和总时间。
- **PIM 时序模型**：
  - PNM（近内存处理）：`tPIM_mem = tin + tarray + tout`（主机-PIM 传输、阵列到 PE 数据移动、输出传输）；
  - PUM（内存内处理）：`tPIM_mem = tin + tprog + tout`（用器件编程延迟替代阵列到 PE 的移动）；
  - 容量超出时使用 `mPIM = ceil(DPIM / CPIM)` 表示重复分区加载的倍数。

### VIPER 框架流程
1. **Profiling 阶段**：用 Linux perf 采集 CPU 侧指令数、执行 CPI、缓存 miss 率、时钟周期等，全部固定；
2. **Sweeping 阶段**：设计者扫描 PIM 侧参数（指令数、计算效率、传输/编程延迟、容量、时钟周期），计算端到端执行时间、加速比、盈亏平衡点、阿姆达尔天花板等。

## 6. 主要结论与发现

- **框架有效性**：
  - 与 gem5 相比，VIPER 平均误差 <10%，97% 的任务卸载预测落在 ±10% 包络内；
  - 数据触发验证中，in-order 规则访问平均误差 4.4%，OoO 不规则访问误差 5.5%，Pearson 相关 r≈0.995；
  - 评估时间从数小时降至 1 分钟以内。
- **真实系统预测**：
  - UPMEM 上先验预测了 Amdahl 天花板（6.57×）、盈亏平衡 DPU 数（约 35）和卸载决策；实测盈亏平衡在 40–49 DPU；
  - 固定传输模型预测单调攀升，但实测显示在 256 DPU 达到峰值 2.46× 后回落的“峰值-滚降”行为；将传输时间修正为随 DPU 数量线性增长的模型后，VIPER 可复现该趋势（12% 平均误差，至峰值处 6%）。
- **架构级设计洞察**：
  1. **主机不可卸载工作是端到端加速的上限**：41–70× 的 XBA 内核加速最终只带来不到 2.96× 的端到端加速；
  2. **容量阈值会产生性能“悬崖”**：容量略小于工作集的交叉阵列性能反而比容量小得多的阵列更差（需反复拆分和重新加载）；
  3. **器件编程延迟决定技术可行性**：数据触发型 PIM（如 IMCRYPTO 安全内存）中，CMOS 和 FeFET 可将开销控制在 10% 预算内，而 RRAM 和 PCM 不可行（13.6% 和 25.0%）。
- **总体结论**：早期 PIM DSE 必须架构感知，电路级评估会遗漏决定成败的跨层成本。

## 7. 优点

- **方法创新**：将 PIM 建模为内存层次结构中的组件而非独立加速器，使 AMAT 框架自然扩展到 PIM 成本，概念简洁而覆盖面广。
- **统一范式**：同一模型同时支持 PNM 与 PUM、任务卸载与数据触发，这是现有工具不具备的。
- **高效性显著**：秒级分析 vs 周期精确模拟数小时，且精度保持在 10% 以内。
- **验证严谨**：既有超过 400 个 gem5 配置的广度验证，又有真实 UPMEM 商用硬件的深度验证，且先验预测与实测吻合度高。
- **实用性**：开源工具，提供清晰的 profiling + sweeping 流程，设计者无需修改模拟器源码即可探索设计空间。
- **案例研究有启发性**：揭示的容量悬崖、技术可行性筛选、最优 DPU 数等结论具有直接工程价值。

## 8. 不足与局限

- **内存级并行（MLP）未建模**：VIPER 基于顺序 stall 的 AMAT 假设，无法捕捉 OoO 执行下的请求重叠，导致 OoO 场景系统性高估延迟；虽然趋势正确，但绝对精度受限。
- **传输模型需要人工修正**：UPMEM 案例中，固定传输假设无法预测峰值-滚降行为，必须由实测数据提炼出线性传输模型后才能与硬件吻合，说明“一次剖析、全空间固定”的假设在某些 PNM 系统中不够完善。
- **容量分区模型简化**：使用 `ceil(DPIM/CPIM)` 一阶近似，未建模 bank 级并行、非均匀数据布局、调度器策略等二阶效应。
- **数据触发验证粒度较粗**：使用聚合 tPIM_mem，未单独验证 tin、tprog、tcomp 分解的准确性。
- **工作负载覆盖有限**：任务卸载验证集中于 GEMM/Llama2 类矩阵乘，案例研究亦以 DNN/加密为主，缺乏更广泛的图计算、数据库、流式计算等 PIM 常见负载。
- **未覆盖能量指标**：论文只建模性能，功耗/能量评估留作未来工作。
- **模拟器异构性**：gem5 与 VIPER 使用不同 ISA（gem5 ARM vs 真实 x86 profiling），因此验证主要基于归一化趋势而非绝对时间，可能掩盖部分建模误差。
