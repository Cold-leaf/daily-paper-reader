## 摘要
LLM推理已成为一项基本服务，但它对内存带宽、计算密度和通信效率提出了前所未有的要求。虽然IMC是解决内存墙问题的一种有前景的方案，但LLM中异构数据的动态性需要互补资源来处理运行期间生成的中间数据。此外，LLM中海量的参数需要规模化架构，其中片上数据移动通常是主要的性能瓶颈。本文提出了一种硬件-软件协同设计框架，将分布式计算、内存和通信统一为一个无缝的处理-通信结构。在硬件方面，我们提出了一种名为LEAP的可扩展架构，它集成了IMC PE、NMC PE和INC。这使得每个硬件层可以执行专门的任务：IMC用于静态权重，NMC用于动态数据，INC用于部分结果归约。在软件方面，我们引入了一个针对LLM服务中关键指标（包括吞吐量和延迟）进行优化的分区、映射和调度框架。为了解决prefill和decode阶段不同的计算强度，我们提出了一种prefill-decode分离方法，该方法动态重新配置PE组织以最大化资源利用率。与商业GPU平台相比，所提出的架构在吞吐量和能量效率上分别提供了$\geq{}1.52\times$和$24.91\times$的改进。

## Abstract
LLM inference has become an essential service, yet it imposes unprecedented demands on memory bandwidth, computational density, and communication efficiency. While IMC is a promising solution to the memory wall issue, the heterogeneous data dynamicity of LLM requires complementary resources to handle intermediate data generated during run-time. Furthermore, the massive number of parameters in LLM necessitates scale-up architectures where on-chip data movement is often the primary performance bottleneck. This article presents a hardware-software co-design framework that unifies distributed compute, memory, and communication into a seamless processing-communication fabric. On the hardware side, we propose a scalable architecture, named LEAP, that integrates IMC PE, NMC PE, and INC. This allows each hardware layer to execute specialized tasks: IMC for static weights, NMC for dynamic data, and INC for partial result reduction. On the software side, we introduce a partitioning, mapping, and scheduling framework optimized for key metrics in LLM serving, including throughput and latency. To address the distinct computational intensities of the prefill and decode phases, we present a prefill-decode disaggregation approach that dynamically reconfigures PE organizations to maximize resource utilization. Compared to commercial GPU platforms, the proposed architecture provides a throughput and an energy efficiency improvement of $\geq{}1.52\times$ and $24.91\times$, respectively.

- **硬件层面的核心挑战**：
  - **异构数据动态性**：LLM 推理中同时包含海量静态预训练权重和运行期生成的动态中间数据。存内计算（IMC）擅长处理静态权重（DSMM），但难以高效处理动态激活（DDMM），需要“IMC+X”架构补充近存计算（NMC）等资源。
  - **单 PE 容量受限**：以 RRAM 交叉开关阵列为例，单个 IMC PE 通常仅能容纳 KB 级数据（典型为 128×128），无法承载十亿级参数的 LLM，必须在数千个空间分布式 PE 上拆分矩阵，导致 NoC 上部分结果聚合与广播的通信负担极重。
- **软件/系统层面的核心挑战**：
  - 如何在异构计算、存储与通信资源构成的规模扩展架构上，优化矩阵切分、空间映射和路由调度。
  - 如何同时满足 LLM 服务在请求级（并发序列竞争）和阶段级（prefill 计算密集 vs decode 访存密集）的不同吞吐/延迟需求。
- **论文主张**：已有工作多聚焦单一层面，缺乏在分布式“IMC+X”加速器语境下覆盖操作级、阶段级、请求级的硬件-软件协同优化研究。为此，作者提出统一了计算、存储与通信资源的协同设计框架 LEAP。

## 2. 论文提出的方法论

### 2.1 核心思想
- 提出三类资源各司其职的统一架构 LEAP：
  - **IMC PE**：存储静态权重并执行静态-动态矩阵乘法（DSMM）；
  - **NMC / 路由内 scratchpad + 路由内计算单元（IRCU）**：暂存动态数据并执行动态-动态矩阵乘法（DDMM）；
  - **INC（in-router computing）**：在 NoC 路由内部完成部分和归约与数据流计算，缓解通信瓶颈。

### 2.2 硬件架构设计（LEAP-A 与 LEAP-D）
- **统一宏单元（macro）结构**：每个宏由 IMC PE + Router 组成；Router 内含 NMC scratchpad、矩阵乘法逻辑（IRCU）与归约逻辑。
- **LEAP-A（聚合模式）**：所有宏同构，共享同一套 IMC+NMC 资源，承担 prefill 和 decode 两种任务。
- **LEAP-D（分离模式）**：
  - Prefill 区域：宏结构与 LEAP-A 相同；decode 区域：移除 IMC PE，scratchpad 扩大一倍（64 KB）以覆盖原 IMC 容量，从而独立承载 decode 阶段的 KV cache 和动态计算；
  - 实现 prefill-decode 空间隔离，资源与存储布局随推理阶段动态重配置。

### 2.3 软件框架
- **划分（Partitioning）**：
  - 权重矩阵按 IMC PE 尺寸沿行、列两个维度切分；
  - 动态矩阵（Q、K、V）按 IRCU 带宽与 scratchpad 容量切分；
  - 划分方式与张量并行+上下文并行的结合类似，但粒度更细，通信在片内高频发生。
- **映射（Mapping）**：
  - 静态矩阵映射遵循启发式：同源子矩阵连续放置、区域尽量矩形、行主序/列主序展开；
  - 动态矩阵（KV cache）在 decode 阶段采用循环追加写入（cyclic storage），以均衡本地存储负载；
  - 跨层（inter-layer）采用蛇形拓扑（serpentine）映射，保证 decode 阶段输出 token 在层间的高效流转。
- **数据流模式**：将片上数据移动抽象为确定的集合通信原语——Broadcast、Reduce、ReduceScatter、AllGather 等，编译期即可确定路由路径，减小运行时控制开销。

### 2.4 阶段级与请求级编排
- **Prefill/Decode 数据流编排**：
  - prefill 以大批量 token 的矩阵乘法为主，精心安排了 Broadcast→MAC→ReduceScatter→AllGather 的多级流水并利用计算-通信重叠；
  - decode 逐 token 处理，LEAP-D 通过将 Q/K/V 广播至 decode 区域所有宏来扩大并行和有效带宽；
  - KV cache 从 prefill 区转移到 decode 区与既有集体通信重叠，不进入关键路径。
- **序列批处理（batching）**：分析了 batch size = 2 的时序调度与资源竞争问题，权衡 TTFT（首个 token 延迟）与 TPOT（每输出 token 延迟）。

## 6. 主要结论与发现

- **架构有效性**：LEAP 通过 IMC、NMC、INC 的明确分工，能同时应对静态权重矩阵乘、动态数据矩阵乘和部分结果归约三类负载，整体在模型规模从 1B 扩到 13B 时仍保持亚线性性能衰减（关键路径只随 se·sl 或 sh·sl 增长，而非全部参数规模）。
- **能效/吞吐优势显著**：
  - 与 A100 相比，LEAP-A 吞吐提升 ≥ 2.55×，能量效率提升 ≥ 71.94×；
  - 与 H100 相比，LEAP-D 吞吐提升 1.52×，能量效率提升 24.91×；
  - 8B 模型 LEAP-A 吞吐 202.25 tokens/s（对比 A100 78.36，H100 274.26），LEAP-D 可达 446.18 tokens/s。
- **PD 解耦有效缩小性能差距**：LEAP-D 显著降低了 prefill 与 decode 的吞吐差异，根本原因是消除了原流水线瓶颈，提高了解码阶段的并行度和存储带宽利用率。
- **通信是主要瓶颈**：关键路径主要由数据搬运与 IRCU 的 DDMM 操作决定，IMC 侧计算很少成为瓶颈；config（64-bit 数据包、16-way IRCU）接近性能前沿。
- **批处理并非全优**：批处理能明显改善 TTFT，但会增加 TPOT——应根据应用的延迟侧重选择批处理或非批处理模式。

## 7. 优点

1. **软硬件协同覆盖完整**：从操作级（DDMM/DSMM）、阶段级（prefill/decode）到请求级（batch），首次给出 IMC 中心架构下较完整的多层次 LLM 推理协同设计；
2. **硬件分工清晰且可扩展**：IMC 处理静态、NMC 处理动态、INC 处理通信归约，规避了“IMC 什么都干”的痛点，支持统一宏单元二维 mesh 扩展；
3. **“PD 分离”的芯片级适配**：将 GPU 集群中的 prefill-decode disaggregation 思想移植到片内异构资源组织中，并给出了 LEAP-A/LEAP-D 两种可切换形态的定量对比；
4. **确定性/编译期数据流**：把高开销的片上通信抽象为集合原语并在编译期确定，降低运行时控制复杂度；
5. **量化实验与面积/功耗分析完整**：给出宏级功耗、面积明细和版图布局，工艺换算、RRAM 参数与数字逻辑皆注明出处，可复现性较强。

## 8. 不足与局限

1. **缺乏流片/实测验证**：性能主要来自指令级模拟器与 45nm 综合/缩放估算，未包含真实芯片测试结果；RRAM 存储单元良率、读写延时、噪声等物理不确定性未被充分纳入系统级模型；
2. **对比公平性风险**：与 A100/H100 的吞吐量对比源于公开规格/报告数据而非同平台实测，功耗对比也缺少对 GPU 真实动态功耗的严格建模；
3. **模型覆盖窄**：仅以 Llama（Decoder-only）家族为例，未覆盖 T5、BERT 等编码器-解码器架构或多模态模型；
4. **应用场景偏向边缘/小型化**：batch 规模仅考察 2，scratchpad/片上 SRAM 容量也偏小，结论难以直接推广到超大上下文窗口（如 128k tokens）或高并发云侧服务；
5. **可靠性策略缺失**：对 RRAM 非易失存储的写次数有限、数据保持力等可靠性问题，以及断电后权重重加载等问题没有讨论；
6. **动态稀疏性与量化空间未探索**：未评估剪枝、稀疏注意力、低比特量化等与 LEAP 架构的协同效果。
