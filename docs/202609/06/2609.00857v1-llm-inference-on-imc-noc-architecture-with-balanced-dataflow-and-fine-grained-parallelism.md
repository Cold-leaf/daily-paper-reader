## 摘要
LLM推理已成为一项关键服务，但它对内存带宽、计算密度和通信效率提出了前所未有的要求。虽然IMC是解决内存墙问题的一种有前景的方案，但LLM的异构数据动态性需要互补资源来处理运行期间生成的中间数据。此外，LLM中海量的参数需要规模化架构，其中片上数据移动通常是主要的性能瓶颈。本文提出了一种软硬件协同设计框架，将分布式计算、内存和通信统一为无缝的处理-通信结构。在硬件方面，我们提出了一种名为LEAP的可扩展架构，它集成了IMC PE、NMC PE和INC。这使得每个硬件层能够执行专门的任务：IMC处理静态权重，NMC处理动态数据，INC处理部分结果归约。在软件方面，我们介绍了一种针对LLM服务中关键指标（包括吞吐量和延迟）优化的分区、映射和调度框架。为了解决预填充和解码阶段的不同计算强度，我们提出了一种预填充-解码分离方法，通过动态重新配置PE组织来最大化资源利用率。与商业GPU平台相比，所提出的架构分别提供了≥1.52倍的吞吐量提升和24.91倍的能效提升。

## Abstract
LLM inference has become an essential service, yet it imposes unprecedented demands on memory bandwidth, computational density, and communication efficiency. While IMC is a promising solution to the memory wall issue, the heterogeneous data dynamicity of LLM requires complementary resources to handle intermediate data generated during run-time. Furthermore, the massive number of parameters in LLM necessitates scale-up architectures where on-chip data movement is often the primary performance bottleneck. This article presents a hardware-software co-design framework that unifies distributed compute, memory, and communication into a seamless processing-communication fabric. On the hardware side, we propose a scalable architecture, named LEAP, that integrates IMC PE, NMC PE, and INC. This allows each hardware layer to execute specialized tasks: IMC for static weights, NMC for dynamic data, and INC for partial result reduction. On the software side, we introduce a partitioning, mapping, and scheduling framework optimized for key metrics in LLM serving, including throughput and latency. To address the distinct computational intensities of the prefill and decode phases, we present a prefill-decode disaggregation approach that dynamically reconfigures PE organizations to maximize resource utilization. Compared to commercial GPU platforms, the proposed architecture provides a throughput and an energy efficiency improvement of $\geq{}1.52\times$ and $24.91\times$, respectively.

- **研究背景**：大型语言模型（LLM）推理已成为现代工业与消费应用的基础服务，但LLM推理对**内存带宽**、**计算密度**和**通信效率**提出了前所未有的严苛要求。传统的冯诺依曼架构面临"存储墙"瓶颈，即在将权重从片外存储搬运至计算单元的过程中消耗大量能量与时间。

- **核心问题**：本文聚焦于以下多个维度的挑战：

  - **硬件挑战1——数据动态性异构**：LLM推理中同时存在海量**静态预训练权重**（适合IMC处理）与运行时生成的**动态中间数据**（如激活、注意力矩阵等）。注意力层中的DDMM（动态×动态矩阵乘法）需要IMC之外的互补计算资源；若采用"IMC+X"架构，则X的选择、比例和协同方式均缺乏系统性研究。

  - **硬件挑战2——PE规模限制与片上通信瓶颈**：单个IMC PE（如基于RRAM的交叉阵列）容量仅KB级（典型128×128单元），而大模型权重矩阵规模达数千维，必须将GB级权重矩阵切分到数千个空间分布式PE上。这种大规模空间分布对NoC提出了高效聚合与归约部分和（partial sum）的极高要求，通信常成为主要瓶颈。

  - **软件挑战1——映射与数据流管理的复杂度**：在异构计算/存储/通信资源（IMC+NMC+INC）上优化矩阵划分、空间映射与数据流路由，是一个极大的搜索空间问题。

  - **软件挑战2——多粒度服务的需求冲突**：LLM推理同时面临请求级（request-level）和阶段级（phase-level）的性能要求；prefill阶段（计算密集型）与decode阶段（存储带宽受限型）对硬件资源的需求相互冲突。

- **研究空白**：上述多维软硬件挑战在分布式"IMC+X"加速器场景中尚未得到综合研究。现有工作要么不涉及INC，要么局限于专用互联和定制设计（见表I对比），缺乏将IMC、NMC、INC统一到可扩展架构并结合软件分区/映射/调度协同设计的完整框架。

### 二、方法论：LEAP架构与软件框架

#### 2.1 总体设计思想

本文提出硬件-软件协同设计框架**LEAP**（Large-scale Efficient Acceleration Platform），核心原则是**"硬件资源专业化分工 + 软件调度确定性协同"**：

- **IMC PE**：存储静态权重，执行DSMM（动态×静态矩阵乘法）；
- **NMC资源（路由器内的暂存器+IRCU）**：存储动态数据，执行DDMM（动态×动态矩阵乘法）；
- **INC（路由器内的归约单元）**：在数据包沿NoC传输的同时执行部分和归约，消除专用聚合器的通信瓶颈。

硬件上每个macro由PE和路由器（路由器集成NMC/INC资源）构成，采用mesh NoC互联，支持模块化复制扩展。两种工作模式：
- **LEAP-A（Aggregated）**：所有macro同构配置，prefill和decode共享资源；
- **LEAP-D（Disaggregated）**：prefill区域同LEAP-A（含IMC），decode区域**移除IMC PE并将暂存器扩展至覆盖IMC容量**。

#### 2.2 静态与动态矩阵的分区（Partitioning）

- **静态权重分区**：权重矩阵沿行、列维度切分，分区大小与IMC crossbar尺寸（128×128）匹配。Q/K/V权重采用列主序划分，O矩阵采用行主序划分。

- **动态矩阵分区**：Q/K/V矩阵切分大小由IRCU带宽和暂存器容量决定；KV缓存采用**循环存储（cyclic storage）**技术，将token向量循环写入暂存器指定区域，保证本地内存负载均衡。

#### 2.3 映射策略（Mapping）

- **层内映射（Intra-layer）**：基于三条启发式规则——(i) 源于同一矩阵的子矩阵映射到连续区域；(ii) 连接区域尽量矩形；(iii) 内部子矩阵遵循行主序/列主序展开。Q/K/V按列主序跨tile映射（V在intra-tile转置而非inter-tile），O按行主序跨tile映射。

- **层间映射（Inter-layer）**：采用**蛇形拓扑（serpentine topology）**安排各decoder层，使自动回归decode阶段的最新输出token能以最短路程传回第一层。

#### 2.4 数据流模式定义

定义了五种确定性的collective数据流模式（编译期可确定，降低运行期控制负担）：
- **Broadcast**：输入向量广播至所有相关PE
- **Reduce**：部分和归约
- **ReduceScatter**：分块归约并散布
- **AllReduce**：全归约
- **AllGather**：全收集

这些模式统一涵盖LLM推理中所有数据移动场景，并支持将MAC计算与通信重叠进行流水线处理。

#### 2.5 Prefill与Decode两阶段调度

- **LEAP-A prefill数据流**：输入tokens广播至Q/K/V权重区→IMC内MAC-1→通道内ReduceScatter-1→K的AllGather-1→NMC内MAC-2（QK^T）→AllReduce（若头维分区）→注意力分数的AllGather-2→MAC-3（分数×V）→O区AllGather-3→IMC内MAC-4→ReduceScatter-2。通过流水线重叠计算与通信（例如AllGather-2与MAC-3重叠）。

- **LEAP-A decode数据流**：与prefill类似，但ReduceScatter-1降级为Reduce-1（因每次仅一个token流入）。

- **LEAP-D设计**：
  - KV缓存仅存储在decode区域；
  - prefill区域的KV转移与AllGather-1/AllGather-2**重叠执行**，不增加关键路径延迟；
  - decode区内有更多不含IMC的macro，可并发访问更多暂存器，获得更高存储带宽并消除计算流水线瓶颈。

#### 2.6 序列批处理

支持批量大小为2的请求并发处理。两块区域中的prefill和decode可在不同请求上重叠执行，但存在对prefill区域IMC权重的资源竞争。文中说明了调度规则，具体场景为：两个请求A（decode中）与B（prefill中）同时需要权重访问时的优先级仲裁策略——若A需要权重而B在做注意力运算，A必须等待；若B在做投影/FFN运算，则B在向量循环中暂停以让A执行。

### 六、主要结论与发现

1. **架构优势**：相比A100，LEAP-A吞吐提升≥2.55×，能效提升≥71.94×；相比H100，LEAP-D吞吐提升1.52×，能效提升24.91×。

2. **性能瓶颈不在IMC侧**：由于计算-通信重叠和高IMC并行度，IMC操作很少占据关键路径；关键路径主要由**数据移动和IRCU中的DDMM操作**主导（图12）。

3. **PD分离效果显著**：LEAP-D能显著缩小prefill与decode阶段间的吞吐差距（4∼6×缩小至接近），通过去除decode区中的IMC（静态权重存储）瓶颈，为更多KV缓存和计算通道释放片上面积。

4. **模型扩展性表现**：模型参数8倍增长（1B→8B）时吞吐并未同步降低8倍，仅随se·sl或sh·sl线性增长，表现为次线性（sublinear）下降，归因于关键路径仅受最大水平/垂直通信路径制约而非总矩阵体积。

5. **批次处理有条件性**：批处理降低TTFT但增加TPOT，并非普适最佳策略。交互式场景（TTFT关键）适用批处理，长文本生成场景（TPOT关键）应选择非批处理。

6. **设计平衡点**：在64-bit包宽 + 16路IRCU并行的配置下系统处于性能前沿，进一步提升将遭遇收益递减。

### 七、方法亮点与优点

1. **统一框架的稀缺性**：首次将IMC（DSMM）、NMC（DDMM）、INC（归约）三类资源统一融入一个可扩展架构，实现了"计算-存储-通信"的紧密耦合。

2. **三级跨度协同优化**：从操作级（单个矩阵乘）、阶段级（prefill/decode）、请求级（调度/批处理）三个层次进行了系统性分析，超越以往仅关注单一粒度的研究。

3. **确定性数据流设计**：编译期确定所有collective模式，降低运行期仲裁负担，是可扩展NoC设计中的重大工程优点。

4. **PD-Disaggregation的片上实现**：在GPU场景中的PD分离依赖高速网络，本文则在单一芯片上通过空间分区和通信叠加实现，中间无跨芯片KV传输开销，并可将KV转移延迟从关键路径上消除。

5. **关键路径工程分析**：系统分解了指令级时序，给出瓶颈所在（数据移动/DDMM，非IMC），并配合roofline分析确定了硬件设计最优工作点，非泛泛而谈。

6. **灵活硬件配置空间**：LEAP-A与LEAP-D双模式从实际上响应了近年来关于prefill-decode聚合与分离之争，给出了体系结构层面的实证结果（而非仅软件层面），并提供了两种模式下的资源权衡关系。

7. **启发式映射引导设计**：利用3条启发式约束大幅降低映射搜索空间，同时给出可复现的映射方案。

### 八、不足与局限

1. **批量处理规模受限**：仅支持batch size=2的场景，远低于现代LLM服务系统的实际需求（典型批次16~64甚至256+）。作者承认"不可与云级应用相提并论"，但对边缘应用的宣称缺乏具体的边缘推理场景基准测试。

2. **模拟验证缺乏流片证据**：所有性能与能效基于Verilog综合 + 模拟器，虽有较完整的EDA流程，但RRAM器件参数的良率、密度、保持力/耐久度特性、温度影响等实战问题未被考虑。文中功率/面积数据沿用[25]的旧有RRAM数据（45nm->7nm缩放），可能过于乐观。

3. **与GPU对比的客观性风险**：GPU是通用处理器，未考虑其共享内存架构下为LLM优化的软件栈（如FasterTransformer、vLLM、TensorRT-LLM等），时钟频率11.4GHz的标称也极不合常规（实际数字芯片频率通常1-3GHz），该吞吐/能效对比的公信力存疑。

4. **模型范围有限**：仅考察Llama系列的decoder-only模型，未评估encoder-decoder（如T5）、多模态LLM或稀疏MoE模型。

5. **规模架构评估不足**：系统扩展性虽然在逻辑上得到论证（模块化复制），但未在模拟中构建和评估千级macro规模的完整系统在NoC拥塞、路由延迟、同步开销下的真实表现。

6. **长序列KV缓存方案受限**：KV缓存为片上SRAM，容量有限；当输入上下文长度超出暂存器容量（如数万token）时，如何管理溢出或外溢缺乏讨论，无法满足超长上下文推理需求。

7. **对INC逻辑的功耗/面积开销与收益权衡分析不足**：路由器占macro 56.32%能量，虽说明其为"数据移动与实时处理主要引擎"，但未单独剥离INC归约逻辑相对于纯路由在能量/面积上的增量开销。

8. **批处理调度策略简单**：仅考虑两请求情况与静态优先级仲裁，缺少动态调度（如基于剩余量/优先级的抢占策略、多请求级联调度、连续批处理（continuous batching））在复杂到达模式下的系统分析。
